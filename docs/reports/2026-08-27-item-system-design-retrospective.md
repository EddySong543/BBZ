## 1. 最重要的结论

道具不是附赠的半点数值，而是玩家付出背包空间、抽取能量、公开槽位和使用时机后获得的一次计划选择。评价一件道具，必须同时看它改变了什么行动、占用了什么构筑价格、失败时损失什么、对手如何反制，以及它能否与多名英雄和其他道具连接。

今后默认遵守以下顺序：

1. 先审完整正式池、储备池、历史否决和24名英雄，再提出候选。
2. 先确定整批基准和结算边界，再逐件决定数值。
3. 机制批次先汇报、确认后整批实装；已明确说“实装”后不反复请求小确认。
4. 实装一次同步运行数据、结算、UI、AI、快照、测试、i18n、图鉴、资产和设计文档。
5. 报告前做全池碰撞、三复制上限、英雄组合、UI负担和实际运行自检。

## 2. 工作流程上的失误与修正

### 2.1 小事频繁确认，大批改动反而未经确认

早期出现过两种相反问题：对局部措辞和普通实现步骤反复询问；对整批稀有道具却在方案未获批准前进入实装。这会让用户承担无意义的微观管理，同时失去对重大方向的控制。

以后采用固定确认粒度：

- **审计和方案阶段**：只读；一次汇报整批旧版、建议新版、强度风险与待裁定项。
- **确认阶段**：机制或整批方向发生实质变化时确认一次。
- **实装阶段**：用户说“采用、通过、实装、更新”后直接完成全部关联修改，不再为常规实现细节逐项打断。
- **新权限或重大歧义**：只有会改变已确认机制、扩大范围或产生不可逆后果时才暂停。

### 2.2 汇报前缺少整批自检

单件看似合理，不代表进入三槽、24名英雄和同时盲选后仍合理。以后提交任何批次前，至少检查：

- 是否符合本档价值基准；
- 三件同名同时使用的最坏结果；
- 是否被同档旧道具严格覆盖；
- 是否与英雄钩子产生意外乘算；
- 所谓 combo 是否真的改变行动选择；
- 对手是否有公共动作层面的反制；
- 是否新增跨回合记忆或常驻UI负担；
- 是否只是历史废案换词、换目标或换资源。

### 2.3 真相源曾经漂移

正式目录、首发文档、全集候选和历史快照曾被混为一谈，造成数量、文案和“是否通过”的判断偏差。固定层级如下：

- 运行时机制与玩家文案：`src/battle/item_catalog.gd`。
- 当前正式池清单：`design/items-firstrelease.md`。
- 审批全集、储备与历史否决：`design/items-list.md`。
- 历史设计过程：`design/items.md`，不能覆盖当前真相源。
- 结算架构：`docs/architecture/ADR-003-item-system.md`。
- 新道具的四维目标规则：`docs/superpowers/specs/2026-08-30-item-four-axis-balance-design.md`；旧 Catalog 与清单只代表尚未重设计的运行现状。

## 3. 定价与稀有度

### 3.1 旧版普通道具基准过低

普通道具普遍只有0.5点收益时，玩家会直接花1能使用可造成1点伤害的「波」。保留低收益道具还会占公开框，形成额外卡手成本。因此，道具不能只按纸面数值与基础动作等价；它还必须补偿构筑空间、抽取成本、公开信息和失败风险。

### 3.2 新的三档职责

- **T1普通**：机制价值通常在 1–2；简洁、稳定或具有清楚读心条件，核心件通常高于 1。
- **T2稀有**：机制价值通常高于 2，不设固定中心或上限；重点不是“T1数值翻倍”，而是连接两个以上公共玩法轴。
- **T3传说**：机制价值通常高于 3，并且必须相对 T1/T2 产生质变。成品可以作为战备资产，不再通过通用图纸或升级链限制准入。

稀有度不等于严格支配。每件道具必须独立比较**机制价值范围、耐久、占格和金币**：耐久与占格都不按稀有度分配；大型廉价件和紧凑高价值件都可以成立；金币贵不能替战斗内超模免责。

### 3.3 不同资源不能按同一倍率换算

1点伤害、1点治疗、1点护盾和1点能量不是同价资产：

- 护盾可跨回合保留，会延长对局；
- 治疗受缺血量和禁疗限制；
- 能量会解锁大波、大防、补充和升级，可能形成循环；
- 穿防、真实伤害和生命支付绕过的防线不同。

数值提基必须通过真实结算和英雄钩子后的有效价值评估，不能统一翻倍。

## 4. 机制设计经验

### 4.1 一句话规则优先

玩家首先需要一眼知道“我现在为什么用它”。复杂度预算应优先留给英雄、同时读招和背包构筑，而不是堆在单件道具的多层 if/else 中。

出现大量“若X则Y，否则Z”时，先检查能否改成更鲜明的结构：

- 选择或改变目标；
- 交换两种已有资产；
- 延迟兑现；
- 设置上限或保底；
- 改写一次结算顺序；
- 牺牲当前资源换取后续计划；
- 操作公开道具栏或背包中的真实物件。

### 4.2 不要在一批里死钻一个体系

稀有道具增补曾过度围绕护盾，导致每件都有用却像同一个公式反复换词。以后每批先做覆盖矩阵：

- 波／大波；
- 攒与能量；
- 防／大防与护盾；
- 生命、治疗、支付与处决；
- 切换、登场和队伍调度；
- 目标选择；
- 命中产生的英雄技能成果；
- 道具栏、背包、耐久与所有权；
- 信息、反制和公开承诺。

同一主题通常不超过一批的约四分之一；真实缺口仍可补，但不能因为已有combo就继续把它同时当入口、转换和出口。

### 4.3 combo必须改变选择

“所有英雄都能受益”只是通用性；“只对一名英雄有用”只是专属配件。合格combo需要说清：

- 哪名英雄因此会改选「波、攒、防、大波、大防或切换」中的哪一项；
- 哪件道具为另一件提供来源、转换或兑现；
- 对手看到公开信息后如何改招反制。

常用检查骨架是“生产端→连接端→兑现端”，但不能为了凑链条新建封闭资源。

### 4.4 道具可以弱化英雄技能，但不能取代英雄身份

停龙剑、寻星坠等证明，英雄技能的弱化一次性版本可以成为好道具。判断标准不是“是否使用同一机制”，而是：

- 道具是否占用空间、次数和使用窗口；
- 是否只提供一次计划，而非每回合稳定改写规则；
- 是否让多个英雄都能形成新选择；
- 是否仍保留原英雄更稳定、更完整或更具角色幻想的版本。

同理，技能文字复制、短时全局沉默、公共动作限制、持续光环和永久战利品下注并非天然禁区；必须通过缩短期限、限制范围、对称生效、提高失败成本或占用更大构筑空间来转译，而不是因参考来源强力就一概排除。

## 5. 必须保持统一的结算语言

### 5.1 命中规则

固定的一句话规则：

> 只有「波／大波」穿过防御时才算命中并结算相关效果；护盾吸收仍算命中，独立道具伤害不算。

额外触发边界：

> 额外触发只重复英雄技能，道具附带效果每次攻击最多结算一次。

这两句防止独立道具伤害提前引爆毒素，也防止双生咒符、聚鼎三花把扭曲的饥渴等道具骑乘效果成倍复制。

### 5.2 必须区分的概念

- 「波／大波」是基础攻击动作；“攻击”不得无意扩大到主动技能、追击或独立伤害。
- “造成伤害”需要经过伤害、护盾、还魂等统一管线；“失去生命”与“支付生命”有不同的保护边界。
- “成功防御”需要攻击真正进入防御门，不能由独立道具伤害误触发。
- “在场”指当前出战英雄；“在队”包含替补；目标和持续时间必须逐句写清。
- 多段攻击的“总伤害增加／减少”按整次攻击结算，不能逐段复制。

### 5.3 长期状态的记忆预算

还魂、真伤待命、定身、封印和多件遗物同时存在时，仅靠头像悬停已经接近认知上限。毒素、脆弱、剑气等战斗状态后续可以通过小标记显式呈现；但这不意味着可以继续无限增加跨回合私有计数。

以后新增长期状态前先问：

1. 能否改为本回合或下一次？
2. 是否能复用现有状态图标？
3. 是否必须持续显示，还是悬停查询即可？
4. 多件同类同时存在时，玩家能否一句话算清？

## 6. 背包构筑带来的变化

### 6.1 背包形状是价格，不是新战斗小游戏

形状只决定占用空间；大量重复形状是正常的。不引入邻接、朝向、连线和专属拼图奖励，避免局外摆包压过局内读招。

每种同名道具最多两件；战斗开始时打乱背包顺序；玩家花1能从真实剩余背包中三选一，未选物随机放回。双方可查看背包轮廓和公开三槽，玩家可查看自己的剩余内容但不知道抽取顺序。

### 6.2 构筑确定性不能消灭局内博弈

战备方案负责让玩家稳定带入计划；随机顺序、付费抽取、抽后公开、有序施放和实例耐久负责保留临场调整。新抽道具本回合可用，不再使用通用部署锁。不要要求每场比赛重新摆包；使用可保存、复制、改名和自动整理的战备方案。

### 6.3 连续远征必须同时保护战利品价值和后续操作空间

胜者需要完整搜索败者背包并按剩余空间拿取，否则多场消耗会让高胜场玩家操作空间越来越少。前两次败场采用同名临时战备件补位，使败者失去真实所有权但不立即失去当前Run的combo；第三败直接出局。系统临时补给只补战备下限，不保留高价值组合。

### 6.4 耐久不是全局模板

药水等消耗品仍应一次性；适合反复使用的器具、护具、法器才考虑耐久。Demo 使用 1–3 次确定性耐久，同一实例每回合一次；耐久跨 Run，但每场结束先退回原背包或保险格，再进行搜刮。增加耐久与复制道具是两种不同价格，前者必须由更大典型占格、更高金币、较低档内单次值或更窄条件承担。

## 7. 参考游戏研究的正确用法

- 研究必须尽量覆盖完整卡牌、物品或技能图鉴，不能只取几张热门样本。
- 先总结原游戏解决的设计问题，再翻译到BBZ的公共接口；不能复制原文、专属资源或表面主题。
- 每批预设计与正式通过池分开记录，避免“研究候选”被误认成当前设计。
- 参考游戏的强机制不应因强度高而直接否决；先尝试降为一次性、短期限、对称、可反制或有真实空间价格的版本。
- 已否决设计不能只换名字、目标、数值或资源后重新提交。

从 Backpack Battles、The Bazaar、Marvel Snap、宝可梦、洛克王国、游戏王和炉石中最值得保留的不是具体文本，而是：构筑价格、有限使用权、公开承诺、来源与兑现、失败推进下一计划、规则短句和清楚的反制窗口。

## 8. 发行分期与内容保密

界面隐藏不等于保密。只要未来道具的名称、脚本、图标或文案进入发行包，就应假定最终可以被解包；PCK加密只能提高门槛。

为避免Demo、首发和未来版本反复人工整理，后续采用：

1. 开发期只维护一份完整道具真相源，并给条目标记 `demo`、`launch_v1`、`future` 或 `rejected`。
2. 每个发行版本使用明确允许名单，自动生成裁剪后的运行目录、图鉴、i18n和资源包。
3. Demo包只包含Demo道具；首发包包含Demo与首发道具；未来道具在开放时通过更新包下发。
4. 发行包继续使用PCK加密，但真正的保密来自“未来内容不进包”。
5. 导出后自动扫描未来道具ID、名称、脚本和图标是否残留。
6. 如果代码仓库公开，未公开内容必须存于私有仓库或私有内容源；从公开Git当前版本删除不能抹去历史泄露。

当前 `ItemCatalog` 会统一预加载全部道具脚本，因此不能只增加一个运行时隐藏布尔值；正式实施分期时，需要由开发期完整源为不同发行配置生成实际裁剪的目录。

## 9. 一件道具的固定实装清单

机制确认后一次同步：

- `ItemCatalog`正式数据、排序、估值、维度、目标和参数；
- 独立`ItemEffect`脚本与`BattleCore`公共结算接口；
- BattleScreen目标选择、提示和图鉴；
- 长期状态小标记或头像悬停信息；
- AI使用条件、目标、候选选择和防浪费逻辑；
- 事件协议、统一校验、快照、clone与中断恢复；
- 模拟统计与相关事件；
- 单件、三复制、英雄组合、道具组合和非法提交测试；
- i18n、关键词、正式文档、全集状态、图标和映射表；
- Godot Import、完整GUT及必要的无截图1920×1080运行验证。

不做无关重构，不覆盖其他工作区改动；占位美术必须明确标记，后续名称与机制确认后再按三方向PixelLab流程制作正式图标。

## 10. 后续工作的正确顺序

1. 从114件当前正式实现中筛选Demo池、正式首发池和未来池，并记录允许名单。
2. 分别审计三个池的公共动作覆盖、每格价值、英雄组合、道具组合和反制密度。
3. 先优化功能与标签，再设计选择性耐久；不能用耐久掩盖本身无用的道具。
4. 实装发行目录生成与未来内容剥离管线。
5. 完成状态小标记、固定形状、耐久实例、残损价格、战末退包与真实背包三选一的运行时迁移。
6. 最后再扩充新道具，优先补真实覆盖缺口，不按现有热门体系继续堆量。
