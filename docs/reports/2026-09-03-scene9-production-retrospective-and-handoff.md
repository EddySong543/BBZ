# Scene9 制作复盘与后续交接

## 1. 最终方向与保护契约

Scene9 的核心读感是“银辉草原、横贯画面的像素云海、远山与固定战斗地面”。浮空岛、瀑布、天空鲸、眼窝发光和程序化草地均已否决，不得因为复用旧代码而重新接回。人物、UI、战斗输入和用户手调构图属于成熟内容，场景专属调整必须隔离在 Scene9。

任何后续优化都先保护四类事实：用户手调节点几何、地面运动平面、明确的前后遮挡关系、已经通过的色彩与节奏。不能用“整体看起来更统一”作为改动这些事实的理由。

## 2. PixelCloud 的正确制作链

### 2.1 资产与复刻

- 以 `scene9_cloud_layer` 的单份原始像素为唯一视觉蓝本，保存完整 RGBA、尺寸、有效区域和哈希；运行时由代码无损重建，不直接加载原 PNG。
- 只允许一份云体，不得横向拼贴、复制纹理、补白或用形状图层重新概括轮廓。两片云层节点共享同一份不可变基础纹理和像素元数据，但各自拥有 Scene9 本地材质状态。
- 修改轮廓必须以源像素坐标和明确掩码进行。红圈删除区与橙圈保护区分别建立契约；不能用大范围裁切、矩形擦除或凭肉眼猜测替代逐像素校对。
- 保留素材自身有限调色板、硬 alpha 与 nearest 采样。新增颜色、半透明边缘、模糊阴影或抗锯齿都会直接破坏像素归属感。

### 2.2 持续动效

- 底部与远景草地接触的最后 8 个源像素深度完全锁定；上缘和侧缘允许 2–6 个源像素的呼吸起伏，不能让整片云漂移或积累位移。
- 内部深色、中间色和高光像素都必须真正改变坐标或成员关系。额外叠一层移动阴影不等于内部纹理在动。
- 总体流向从瀑布曾对应的中心向左右展开，水平位移是主导，垂直相位权重为零；禁止整齐向下流动、全层单向平移或长期跑出画面。
- 慢速像素动效出现卡顿时，不通过加速掩盖。使用亚像素时间相位、相邻离散采样的时间插值和仅限运动边缘的过渡混合；空间采样仍保持源像素整数格与 nearest 语言。
- 动画循环首尾必须连续，每一小步都发生可测变化，不允许循环点停一帧或冻结后重启。

### 2.3 点击涟漪与性能

- 点击只命中当前帧真实不透明云像素；重叠云层按画面最前方命中，复制的第二层也必须独立响应。
- 同一区域重复点击不能刷新或取消旧涟漪。使用三个独立槽位让响应自然重叠，每个槽位保留自己的中心、年龄和包络。
- 涟漪同样锁住底缘，不用外部模糊、光晕或整层透明度变化伪装内部响应。
- 基础图像只构建一次。持续动画与点击响应由 GPU 材质完成，运行时不得逐帧 `ImageTexture.create_from_image`、`update` 或上传整张云图。

### 2.4 PixelCloud 验收门槛

- 源尺寸、RGBA 哈希、有效区域、单份覆盖、无左右补白全部固定。
- 动画后调色板外颜色为 0；暗部、中间色、高光、左半与右半均有足量变化。
- 上部轮廓有明显变化，最大位移保持 2–6 源像素；底部轮廓变化严格为 0。
- 流向必须报告为 `outward_from_impact`，18 秒循环首尾一致，任意相邻子帧都不能冻结。
- 两个云节点共享基础纹理但材质实例互不污染；性能审计中运行时纹理上传为 0。
- 只看脚本或编辑器基础场景不算验收。必须实例化真实 Scene9/BattleScreen9，验证节点树、可见性、材质实例、shader 时间链、输入链和最终像素数据。

### 2.5 本轮 PixelCloud 失败模式

- 直接沿用原资产，只做整体平移：内部和轮廓没有生命感，且时间久后露出素材边界。
- 用圆角块或形状图层拼云：轮廓像电视雪花，像素密度和场景资产完全脱节。
- 横向拼贴与补白：产生接缝、重复节奏和左侧多余下垂段。
- 只移动外部阴影：看似有变化，实质云体深浅像素完全静止。
- 用软扭曲或模糊处理轮廓：破坏硬边像素与底部接地关系。
- 参数微调代替运行链排查：当“完全没动/完全没变”第二次出现后，必须停止调参，改查真实根场景、节点脚本、材质复制、shader `TIME`、process/input、层级和 UV。
- CPU 重建图片驱动动画：画面可能接近目标，但会让 Scene9 明显卡顿，最终必须转为一次构建、GPU 重映射。

## 3. 场景分层、接地与调色经验

- Platform、远景草地和道路属于同一个固定地面运动平面，不参与鼠标横向视差；ForegroundMid 与左右近景属于更近的独立运动平面。
- 多块 Platform 先统一像素密度和比例，再合成为单一地面。禁止为掩盖接缝添加来源不明的银草延伸、连续接地边、散点或模糊渐变。
- 远景草地与战斗平台的连接优先使用素材自身重叠、局部投影、草缘遮挡和色阶连续性；通用的黑边、像素带或新增道路延伸会制造第二条错误边界。
- 调色必须以整幅画面为单位建立同一套亮部、主体色和阴影色阶。把中景简单去饱和到白色会像“失去颜色”；银白仍需承接天空和云层中的冷暖关系。
- 用户已经手调的位置优先于自动构图假设。修剪道路或云体时只改像素内容，不顺手改变节点位置、尺寸或缩放。

## 4. 风场、近景与粒子经验

- 远景草原、远山植被和近景枝叶都采用根部固定、上部摆动的局部网格形变；不同层使用独立相位、幅度和速度，不能整层平移或同步摇摆。
- 近景枝叶需要可读，但轮廓不能脱节；验收同时设置最小可见位移和最大安全位移，不能只限制“不要太大”。
- 稀疏粒子意味着数量更少、每个仍然可读，不等于缩成看不见的点。1920×1080 下远层先以 8–12 px、近层 14–24 px 为基线，再通过减少数量和降低对比度让它融入场景。
- 当新设计多次不合格时，应优先复用已经通过的 Scene2 粒子语言并只调整数量、速度、深度色和生成区域，而不是反复创造新形状。
- 草地点击沿用 Scene5 的向上抛草屑语义；同一位置的多次点击应生成独立组并重叠，不能刷新前一组。

## 5. 彩蛋与遮挡语义经验

本轮从鲸鱼、眼窝发光到眼窝飞鸟，最大的问题不是参数，而是彩蛋载体与远景尺度不匹配。远景彩蛋应借用现有地标、短时可读、低频出现，不应凭空加入高清巨物或大面积形状层。

飞鸟最终契约如下：8 只 5×3 源像素鸟分批出现，三帧振翅，沿右上方弧线运动；作为左山后绘制子节点，始终完整处于山体前方，不使用山体 alpha、眼窝连通域、安全边距或整鸟裁切。结束阶段在继续移动的同时用 1 秒平滑透明度包络淡出，禁止原地停顿后消失。

“穿模”不是可执行的层级规格。它可能表示本应被遮挡却画在前面，也可能表示本应完整在前却被裁切。以后遇到此类反馈，必须先写成一条明确关系：`A 始终在 B 前`、`A 只在 B 的 alpha 内显示` 或 `A 进入 C 后被遮挡`。测试也必须锁定用户想要的呈现语义，而不是锁定一次误解后的实现手段。

## 6. 协作与排障门槛

- 对明显的小范围 Scene/UI 修改直接执行，不反复提供不可能采用的方案；但遇到前后关系、运动平面、是否允许裁切这类会改变结果模型的歧义，要先在内部转成明确契约再动手。
- 用户圈图用于定位像素，不自动等同于节点变换授权。先把圈选区域映射回源像素坐标，用测试保护“删除区”和“不可删除区”。
- 同一视觉症状第二次被报告为“完全没变/还是原样”时，禁止继续调同一组参数。必须检查真实运行入口、节点实例、坐标链、绘制顺序、资源是否实际引用以及像素输出。
- 每个阶段完成后写清楚：保留了什么、否决了什么、哪些数值可调、哪些是保护契约。否则后续优化容易把已通过内容重新引入回归。

## 7. 后续交接检查表

1. 修改前先读本文件、`assets/scenes/scene9/README.md` 和 Scene9 契约测试。
2. 不重新接入浮空岛、瀑布、鲸鱼、眼窝发光、程序化草地或旧云拼贴方案。
3. 不改变用户手调构图、固定地面平面和现有前后层级，除非任务明确点名。
4. 云层修改必须同时通过源像素、动效连续性、交互重叠和零运行时上传检查。
5. 视觉修复使用 Godot 日志、几何断言和像素数据验证，不生成或提交截图。
6. 若改动触及共享 Battle Screen，额外验证 Scene1–8 的成熟行为未被 Scene9 专属逻辑污染。
