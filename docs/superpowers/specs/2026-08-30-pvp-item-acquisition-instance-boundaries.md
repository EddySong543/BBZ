# PvP 道具取得与实例边界（任务 1 封板）

> ⏸ **状态覆盖（2026-08-31）：**PvP 运行时与产品入口已冻结。手动免费三选一、空框限制、取得后锁定本回合和逐次使用费已经上升为 PvE / PvP 通用规则；本文继续保存多人同步、超时、断线、服务器实例与重连等未来 PvP 专项边界。
> **状态：已批准；任务 1 的专项真相源。** 本文补全道具系统当前标准中的开局、抽取阶段、候选不足、同名实例、框位释放、超时 / 重连以及交换 / 复制实例边界。
> **适用范围：**第 1–5 节的取得核心由当前通用标准引用；多人同步、断线、权威服务器和跨方资产冲突部分仅适用于未来 PvP。本文描述目标规则，不表示当前运行时已经迁移。
> **冲突裁定：**与旧起手道具、旧 `1` 能补充、旧槽位解锁、旧断线冻结或旧复制语义冲突时，以本文和 [`2026-08-30-item-system-current-standard.md`](2026-08-30-item-system-current-standard.md) 为准。

## 1. 一页结论

1. 双方以 **3 个空公开道具框**开局，不随机、指定或预置任何可用道具。
2. 每回合先经过独立的同步抽取阶段，再开始完整行动规划；抽取本身免费且每人每回合至多一次。
3. 候选是当前真实战斗背包里的实例，按 UID 无放回展示 `min(3, N)` 件；不足 3 件不补假道具。
4. 同名但 UID 不同的实例可以同时成为候选；重复携带用占格、价格、资产风险与构筑广度换检索稳定性。
5. 第 `R` 回合取得的实例进入公开框并锁定，第 `R+1` 回合才可使用。
6. 耐久在第 `R` 回合归零的框到该回合最终清理才腾空，因此最早在第 `R+1` 回合重新获得抽取资格。
7. 抽取超时自动放弃；行动超时自动提交“攒 + 空道具序列”。断线不暂停阶段时钟，Demo 初始保留席位 30 秒。
8. 实例采用“资产归属 + 当前控制”双身份。战斗内交换不改变真实资产归属，战后先归还，再进入正常搜刮。
9. “复制效果”只重放一次已结算效果，不生成实例；“复制实体”必须生成新 UID，并默认是仅本场存在的临时件。
10. Demo PvP 不开放通用单件偷取，也不提供免费丢弃 / 销毁按钮；高风险资产操作必须由具体内容专项审批。

这套边界只增加一个玩家需要理解的主流程：

`先决定是否拿一件 → 双方同时看见结果 → 再规划本回合`

其余复杂性留在服务器实例与结算规则中，不增加玩家必须背诵的隐藏例外。

## 2. 权威回合时序

每回合采用以下时序：

```text
RESOLVE_(R-1)
→ END_(R-1)：回合末触发、死亡结算、强制换人
→ CLEANUP_(R-1)：清除耗尽实例并腾框
→ START_R：跨回合状态到期，旧 LOCKED 转为 READY
→ DRAW_R：双方私密决定抽取或放弃
→ DRAW_REVEAL_R：服务器原子落账并同步公开结果
→ PLAN_R：双方获得完整且等长的行动规划时间
→ RESOLVE_R
```

裁定如下：

- `DRAW_R` 是行动规划前的独立同步门，不与行动倒计时混在一起。
- 抽取阶段中不能提交公共行动或道具序列；双方最终状态确定后才进入 `PLAN_R`。
- 新取得件写入 `usable_from_round = R + 1`。即使使用费为 `0`，本回合也不能使用。
- `DRAW_REVEAL_R` 是零持续时间的服务器事务：实例转移、公共快照升级与切换到 `PLAN_R` 必须原子完成，再用同一条消息公布结果和行动截止时间。
- 行动规划计时从该原子事务完成后才开始，不能让先点击者多获得规划时间；客户端必须先应用消息绑定的公共版本，才能开放规划输入。
- 只有双方公开框都没有 `VACANT` 时才根据公开信息跳过 `DRAW_R`。只要任一方有公开空框就进入抽取阶段，不能因私密背包已经为空而提前结束或跳过。
- Demo 抽取窗口初始值为 **8 秒**；行动窗口暂沿用当前 **10 / 15 / 20 秒**阶梯。具体秒数属于可调参数，两段式结构不是调参项。

## 3. 开局与第一件道具

- 双方 3 个公开框开局都为 `VACANT`。
- 第 1 回合正常进入 `DRAW_1`，没有赛前“第 0 回合”抽取，也没有起手保底件。
- 第 1 回合选中的道具公开为 `LOCKED`，第 2 回合开始转为 `READY`。
- 第 1 回合不抽、放弃或没有合法实例，不会在之后补发；每回合机会互相独立且不能累计。
- 白手战备可以正常参战；背包为空且有公开空框时，本人只会收到“没有可抽取道具”并确认放弃，不影响五种公共行动，也不向对手泄漏背包余量。

不采用预置件的原因不是压低道具存在感，而是保持统一的信息规则：任何道具第一次进入公开框，都必须给对手一个完整回合的观察窗口。起手件不应绕过这条规则。

## 4. 抽取资格与候选

### 4.1 抽取资格

服务器在 `DRAW_R` 开始时冻结本轮判定快照。玩家同时满足以下条件才是 `AVAILABLE`：

- 本回合抽取额度尚未使用；
- 至少有一个 `VACANT` 公开框；
- 当前战斗背包中至少有一个合法实例。

合法实例必须：

- 位于该玩家本场可抽取的战斗背包；
- 没有位于公开框、其他容器或销毁记录；
- 未被目标版本的 `demo_enabled` 规则隐藏；
- 其 UID、耐久和临时生命周期都能由服务器验证。

没有 `VACANT` 框属于公开的 `BLOCKED`。有空框但合法实例为 `0` 时属于私密的 `NO_CANDIDATES`：只向本人显示“背包中没有可抽取道具”，本人仍需确认放弃，或等待超时；服务器不能让该私密状态自动提前结束公共阶段。

### 4.2 候选数量

设合法实例数为 `N`：

| `N` | 展示结果 |
|---:|---|
| `0` | 不生成候选；本人确认放弃或等待超时 |
| `1` | 展示该 1 件与“放弃” |
| `2` | 展示该 2 件与“放弃” |
| `≥3` | 按 UID 无放回随机展示 3 件与“放弃” |

空候选位只显示“背包中没有更多道具”，不能放入系统白板、虚拟副本或同一实例的重复影子。

当前基线中，每个合法 UID 的基础概率相同，按 UID **等概率无放回**抽取；默认没有英雄、稀有度、耐久、名称或旧维度加权。重复携带几件，就真实增加几张抽取票。

### 4.3 同名实例

- 抽样按 UID，不按 `item_def_id` 或名称去重。
- 两件同名道具若 UID 不同，可以同时出现；候选 UI 显示各自的当前 / 最大耐久，并明确区分“本次 Run 临时”与“本场临时”。
- 玩家选中其中一件时，只转移该 UID，另一件仍在战斗背包。
- 若某类道具需要限制携带数量，必须在赛前战备规则中公开限制，不能在候选阶段暗中合并。

这会形成明确构筑取舍：小背包和重复件提高核心件命中率，但减少工具广度，并承担对应的占格、金币与真实资产风险。若“单件 T3 全押”实测成为统治解，应调整该件使用费、耐久、占格、价格或公开的携带上限，而不是伪造三选一。

### 4.4 候选固定与随机权威

- 第一次打开后，服务器内部以 `asset_uid` 固定候选；只向本人返回不可变的 `offer_id`、对应 `candidate_handle` 与固定顺序。
- 关闭浮层只是本地行为，不取消、不刷新也不重新随机。
- 重复打开、重发请求或重连都返回同一个 `offer_id` 和同一候选。
- 候选随机使用永不下发客户端的服务器私密 `draw_secret`，结合比赛、回合和席位派生；不能复用会进入 BattleCore 快照的 RNG，也不能因网络包到达先后改变结果。
- 玩家可以不打开候选而直接放弃；此时不生成 `offer_id`、不抽样，也不推进候选随机流，但会消耗本回合机会。
- 玩家从未打开且一直未操作时，超时直接进入 `TIMEOUT_PASS`，同样不生成候选；已经 `OFFERED` 后放弃或超时，则保留原候选记录但不转移任何实例。
- 选择或明确放弃一旦由服务器确认就不可修改；放弃消耗本回合机会。

## 5. 同步提交、入框与公开信息

每名玩家的抽取状态为：

| 状态 | 含义 | 后续 |
|---|---|---|
| `BLOCKED` | 无公开空框；该状态本身是公开信息 | 终态 |
| `NO_CANDIDATES` | 有空框但无合法实例；仅本人可见 | `PASSED / TIMEOUT_PASS` |
| `AVAILABLE` | 可以抽取，尚未打开 | `OFFERED / PASSED / TIMEOUT_PASS` |
| `OFFERED` | 已打开并收到私密候选 | `PICKED / PASSED / TIMEOUT_PASS` |
| `PICKED` | 已承诺一个实例 | 终态 |
| `PASSED` | 主动放弃 | 终态 |
| `TIMEOUT_PASS` | 超时放弃 | 终态 |

- 选择发生时，服务器先私下记录承诺，不立刻更新公共框。
- 公开 `BLOCKED` 席位直接视为终态；其余席位都通过本人输入到达终态或抽取阶段超时后，服务器在一次事务中转移选中实例、升级公共状态并进入 `PLAN`。
- 抽取阶段中，冻结快照涉及的战斗背包与公开框不能被其他流程修改；揭示时若服务器内部候选 `asset_uid` 或目标空框与快照不一致，属于权威状态错误，必须回滚 / 恢复事务，不能静默改成放弃或重抽。
- 有多个空框时，取得件进入**编号最小的空框**。框位本身没有邻接、朝向或战斗加成，因此不增加一次无意义的摆放点击。
- 未选实例始终保留原耐久与位置；服务器不能先移出再错误复制回去。
- 对手只看见最终取得的道具，或统一的“未取得”；不区分主动放弃、超时、没有候选，避免泄漏背包余量。
- 公开信息至少包含名称、当前规则文案、逐次使用费、当前 / 最大耐久、`LOCKED / READY`，并明确区分“本次 Run 临时”与“本场临时”；不公开资产 UID 或保险绑定。

## 6. 框位生命周期

公开框采用以下可见 / 权威状态：

```text
VACANT
LOCKED
READY
USED_THIS_ROUND
DEPLETED_PENDING
```

### 6.1 正常使用与耗尽

- 同一实例每回合最多使用一次。`USED_THIS_ROUND` 由实例字段 `last_used_round == R` 推导，不是留在槽位上的另一份状态。
- 合法使用后若剩余耐久大于 `0`，实例从 `READY` 变为 `USED_THIS_ROUND`；到 `START_(R+1)` 才重新成为 `READY`。实例本回合被移动或交换时，已使用记录跟随 UID。
- 道具步骤仍按“合法性检查 → 支付使用费 → 扣 1 耐久 → 结算效果”执行。
- 扣减后耐久为 `0` 时，该次效果仍完整结算；随后实例进入 `DEPLETED_PENDING`。
- `DEPLETED_PENDING` 从此不能再使用、被复制实体或成为普通目标，但该框在本轮余下结算中仍不算空框。
- 本轮所有序列、跨方结算、死亡与回合末效果完成后，`CLEANUP_R` 才发出 `slot_vacated` 并转为 `VACANT`。
- 因此第 `R` 回合耗尽的框最早在 `DRAW_(R+1)` 提供新的抽取资格。
- 比赛在本回合结束时仍必须完成耐久落账与清理，只是不再开启下一次抽取。

### 6.2 移动、退回与原位替换

- 一个仍存活的实例被合法移出公开框时，原框在该步骤完成后立即 `VACANT`；因为抽取阶段已经结束，这不会产生同回合额外免费抽取。
- 后续明确的移动或生成效果可以利用该空框，顺序因此可能产生真实差异。
- 普通效果不能占据 `DEPLETED_PENDING` 框；只有文本明确写明“破碎后原位生成 / 替换”的同一个原子效果可以接管该位置。
- 交换两个已占用框属于一次原子操作，不要求先制造中间空框。
- 整段序列若在克隆状态预演时基础非法，仍按现行规则原子拒绝，不产生部分腾框或部分耐久损耗。

## 7. 超时、断线与重连

### 7.1 超时默认动作

- 抽取阶段超时：记为 `TIMEOUT_PASS`，绝不随机替玩家选择或消耗真实资产。
- 行动阶段超时：若尚未合法提交，服务器提交“攒 + 空道具序列”。客户端未提交的拖拽编排不进入权威状态。
- 已经合法提交后断线或超时：保留原提交，不能用重连撤销或修改。
- 所有截止时间以服务器单调时钟和收包时盖下的 `received_at` 为准，不信客户端时间。`received_at <= deadline` 有效，之后无效；每次收口先处理全部截止内已入队命令，再原子关闭阶段。

### 7.2 断线不冻结比赛

- 单方断线不暂停抽取或行动时钟，也不顺延阶段截止时间。
- 重连只获得当前剩余时间，不重开阶段、不刷新候选、不重置行动倒计时。
- Demo 初始为断线席位保留 **30 秒**。首次断线开始计时，短暂反复上线不能刷新这 30 秒；玩家稳定在线经历一个新的完整规划阶段后，才视为新的断线事件。
- “稳定在线经历完整规划阶段”严格指连续在线覆盖一次 `PLAN_BEGIN → 本人合法提交或 PLAN_END`。
- 30 秒到期仍未恢复则掉线方判负。正常战斗终局与断线终局按服务器事件时间先形成者生效，后者不能覆盖前者；同一检查批次已经产生正常战斗终局时以正常终局为准，否则双方都到期则一次性记为无效局，不按玩家编号先判一方失败。
- 若自动“攒”期间战斗已经按正常规则结束，以战斗结果为准。
- 当前玩家宿主进程消失会同时带走权威房间；正式 Rank PvP 要完整支持该规则，仍需中立权威服务器或房间迁移，不能只靠客户端重连伪装解决。

### 7.3 重连快照

本人重连快照至少包含：

```text
round_id
phase + phase_revision
seat_epoch
public_state_revision + private_draw_revision
server_now_ms + phase_deadline_ms
本人 draw_state
本人 offer_id 与私密候选（若已生成）
本人已承诺的候选句柄、目标框与提交回执（若存在）
公共道具框、耐久和锁定状态
权威事件游标 + 此游标之后的表现事件增量
```

- 快照不得包含对手未揭示候选或选择。
- `OFFERED` 恢复原候选；`PICKED` 向本人恢复“已选定，等待同步公开”和本人选中结果，公共框仍为 `VACANT`；`PASSED / TIMEOUT_PASS` 只显示决定已提交。三者都不能改选，对手在 `draw_reveal_and_plan_begin` 前看不到变化。
- 结算中重连从最后确认事件游标续播，不能再次扣费、耐久或重复生成实例。
- 事件增量只驱动表现，不再次应用状态副作用；历史已经裁剪时执行硬快照恢复并跳过缺失动画，不能猜测或重放旧副作用。
- 服务器为每个席位维护 `seat_epoch / active_connection_id`。新连接成功接管时递增代次，旧连接及其尚未处理的入队命令立即失效。
- 未提交的本地序列不是服务器真相；客户端进程仍在时可以本地保留，进程丢失时只能在剩余时间内重编。

## 8. 实例单一真相与生命周期

服务器维护唯一实例注册表，背包、候选、公开框和销毁记录只引用 UID，不复制整份实例数据。

```text
ItemInstance
- uid
- item_def_id
- asset_owner        战斗结算时的归还对象
- controller         当前战斗中可操作该件的一方
- location           战斗背包 / 公开框 / 销毁记录
- slot_index
- durability_current / durability_max
- lifetime           REAL / RUN_TEMPORARY / BATTLE_TEMPORARY
- pending_destroy
- usable_from_round
- last_used_round
- created_by_event_id
```

硬性不变量：

- UID 在其有效的仓库 / Run 生命周期内唯一且永不复用。
- 任一存活 UID 同一时刻只位于一个容器；候选只是对实例的只读引用。
- `asset_owner` 与 `controller` 分离。战斗内控制权变化不等于永久获得资产。
- 真实实例的耐久、保险绑定和资产归属跟随 UID，不跟随槽位字典复制。
- 生命周期在战斗内只能保持或缩短，不能把 `BATTLE_TEMPORARY` 延长为 `RUN_TEMPORARY`，也不能把任何临时件变成 `REAL`。
- `pending_destroy` 实例在清理前仍位于原公开框；销毁记录是清理后的审计墓碑，不是存活实例容器。

三种生命周期：

| 生命周期 | 结算语义 |
|---|---|
| `REAL` | 可持久化、正常搜刮和兑现；剩余耐久跨 Run 保留 |
| `RUN_TEMPORARY` | 正常显示战斗估值，兑现价值为 0；不能出售、保险、搜刮或带出，Run 结束删除 |
| `BATTLE_TEMPORARY` | 正常显示战斗估值，兑现价值为 0；当前战斗结束即删除 |

旧的单一 `temporary: bool` 不足以区分后两者，迁移时必须改成明确生命周期。

### 8.1 资产 UID 不直接下发客户端

同一实例按接收者使用三层身份：

- `asset_uid`：服务器持久真相，只用于实例注册表、结算与反作弊，默认不下发；
- `controller_handle`：只发给当前控制方，用于抽取选择和提交序列；
- `public_token`：本场短期公开标识，双方只用来对应动画、框位和动作列表，不能反查持久资产。

跨方交换后，服务器向新控制方签发新的 `controller_handle`，旧控制方句柄立即失效。重连只恢复本人当前有效句柄；候选、公共事件和对手快照都不能泄漏 `asset_uid`。

`candidate_handle` 只在对应 `offer_id` 内有效；未选候选的句柄在抽取阶段结束时全部失效。选中件在原子揭示时获得控制方句柄与公共 token，不能继续拿候选句柄提交使用。

## 9. 移动、交换与偷取

### 9.1 己方框内移动 / 交换

- 移动原 UID，不创建实体。
- 保留耐久、生命周期、资产归属、锁定回合和本回合已使用记录。
- 单纯改变己方框位不会重新锁定；原本可用且本回合未使用的实例，后续步骤仍可使用。
- 服务器序列最终解析到 UID；客户端提交本人有效的 `controller_handle`，槽号只用于验证当前位置和播放动画，防止换位后误用另一件同名道具。

### 9.2 跨方整体交换

- Demo 只保留经过单件内容审批的**整体、对称交换**原语，不开放任意目标的通用交换按钮。
- 交换移动原 UID，保留耐久、生命周期与 `asset_owner`，只改变公开框位置和 `controller`。
- 新控制方本回合不能立即使用：`usable_from_round = max(原值, R + 1)`。
- 整体交换包含三个完整框状态：`VACANT`、锁定件、已用件和 `DEPLETED_PENDING` 都按原位置一起交换。待销毁实例不会复活，只会在新位置完成本回合清理。
- 交换件自身若扣耐久后仍存活，会作为原 UID 一起交换并锁到下回合；若已进入 `DEPLETED_PENDING`，则随完整框交换后在清理时消失。
- 双方同时产生同一种整体交换时，在统一跨方结算点按有效次数奇偶处理：偶数次抵消，奇数次交换；不得按玩家编号或网络先后决定。
- 整体能量交换若与该效果绑定，也在同一个对称结算点处理。
- 这类跨方全局效果默认 `effect_replayable = false`，不能借普通复制效果绕过专项成本。

### 9.3 通用单件偷取暂不进入 Demo

Demo PvP 不允许任意偷取对手一件真实道具。它不是数值禁区，而是同时引入目标已提交使用、空框冲突、资产恶意损耗和跨方先后手，当前收益不足以覆盖规则成本。

若以后作为传说、事件或 PvE 专项加入，最低边界为：

- 只能移动对手公开框中的原 UID 到己方明确空框，不能直接塞入私密背包；
- 资产归属不变，新控制方锁定一回合；
- 对方本回合已经合法提交的使用不被网络先后抢断；若目标在结算时已耗尽，偷取失效但偷取件仍付费、扣耐久；
- 多个跨方操作争夺同一 UID 或目标框时全部冲突失败，不按玩家编号抢先。

## 10. 复制效果、复制实体与生成

### 10.1 复制效果

以“再次结算上一件符合条件的道具效果”为标准。提交预演会把复制件绑定到前方那一个明确的来源步骤，不能在结算时临时回退到更早的道具：

- 不创建实体、不分配 UID、不占用新框。
- 来源必须是前方一件定义允许复制的道具步骤；提交时不存在来源或来源定义不可复制，整段序列基础非法并原子拒绝。
- 权威来源事件是该步骤成功产生的 `ITEM_EFFECT_RESOLVED`，其 `effect_payload` 至少冻结来源事件号、道具定义、原目标、分支、数值参数与随机结果。
- 重放沿用原目标、分支、选择和随机结果，但在当前状态重新计算效果，不能直接再次写入上一次的生命、能量或状态差值。
- 只支付复制件自身的使用费并扣复制件耐久；原实体不再次付费或掉耐久。
- 产生 `ITEM_EFFECT_REPLAYED`，不产生第二个 `ITEM_USED`；重放事件不更新“上一件道具”，也不能成为新的复制源。
- 原实体之后已经耗尽，不妨碍重放其历史效果。
- 来源步骤或原目标因对手本回合动态反制而没有产生可用 payload 时，本次重放收益为 0；复制件仍消耗费用和耐久，且不能改为复制更早的道具。
- 道具定义必须显式允许 `effect_replayable`。复制、跨方整体交换、永久资产操作与复杂生成默认不可重放。

### 10.2 复制实体

- 服务器分配全新 UID，不能复用或派生出可猜测 UID。
- 默认生命周期为 `BATTLE_TEMPORARY`，不能复制出可撤离真实资产。
- 继承源实例的道具定义、最大耐久与复制当刻的剩余耐久；不继承 UID、保险、位置、锁定、本回合已使用记录或已经挂到角色上的持续效果。
- 不继承源实例的归属与控制；新实例初始化为 `asset_owner = controller = 创建方`，仅供本场结算与审计使用。
- 目的地必须由效果明确写为公开框或战斗背包，不能发生隐式溢出。
- 进入公开框时必须有合法空位，并锁定至下回合；进入战斗背包时最早参与下回合候选，之后仍遵守正常取得锁定。
- 如果设计只想给予一次额外使用，玩家文案必须明确写“生成一件耐久为 1 的同名临时道具”，不能把“复制”暗中统一削成 1 耐久。

### 10.3 生成临时件

- 按指定 `item_def_id` 生成新 UID；默认满耐久、`BATTLE_TEMPORARY`、锁定至下回合。
- 新实例初始化为 `asset_owner = controller = 创建方`。
- 只有战后奖励或文本明确写“本次 Run”的系统才能生成 `RUN_TEMPORARY`。
- 战斗内效果不能把已有 `BATTLE_TEMPORARY` 延长为 `RUN_TEMPORARY`，也不能把任何临时件转为 `REAL`。
- 没有合法目的地时生成失败；若该步骤在提交预演时本就非法，则整段拒绝；若因跨方结算才失效，则生成件仍付费、扣耐久但效果为 0。
- 临时件正常显示同耐久真实件的战斗估值，但兑现价值始终为 0。

## 11. 主动销毁与战后归还

- Demo 不提供免费右键丢弃或主动销毁按钮，否则“有耐久就占框”失去意义。
- 只有具体道具效果或明确系统结算可以销毁实例。
- 作为成本主动销毁时，只能选择自己控制且资产也属于自己的实例；交换后暂时控制的敌方真实件不能拿去烧毁。
- 正常使用暂时控制的敌方实例仍会扣该原实体耐久；这是跨方交换内容必须承担并公示的风险。
- 销毁后 UID 仍位于原框，但立即标记 `pending_destroy` 并进入 `DEPLETED_PENDING`，不能再操作；`CLEANUP` 时才移入销毁记录并腾框。原位替换则在同一原子事务中完成墓碑化与新实例入框。
- 先销毁 A、后面又安排使用 A 的序列在克隆预演中整体非法，不能只执行前半段。
- 普通 PvP 道具不得直接无条件永久抹除敌方真实资产；敌方干扰优先使用本场锁定、受控耐久损耗或可预判的专项效果。

战斗结束按以下次序处理：

1. 落账所有耐久与耗尽实例；
2. 直接删除全部 `BATTLE_TEMPORARY`，不触发退包、归还、搜刮或临时战备事件；
3. 只有幸存的 `REAL / RUN_TEMPORARY` 按 `asset_owner` 归位，并重置 `controller = asset_owner`，不把本场交换控制权带入下一场；
4. 再按连续 PvP Run 规则进行保险、搜刮、同名临时战备与撤离结算；
5. 只有正常战后搜刮 / 结算可以改变真实资产归属；事务提交时同时设置 `controller = 新 asset_owner`，下一场再映射到该持有者的比赛席位。战斗内交换不能洗成永久所有权。

前两败同名临时战备使用以下实例语义：胜者实际搜刮的是原 `REAL` UID，保留其战后剩余 / 最大耐久，并在搜刮事务提交时改变 `asset_owner`；败者同时获得一个全新 UID 的 `RUN_TEMPORARY`，继承该件战后剩余 / 最大耐久，`asset_owner = controller = 败者`。没有被搜刮、已经耗尽或主动销毁的实例都不会生成替代件。

## 12. 最小网络命令与事件

```text
S2C draw_phase_begin
C2S draw_open
S2C draw_offer_private
C2S draw_pick / draw_pass
S2C draw_commit_ack_private
S2C draw_reveal_and_plan_begin
C2S submit_sequence
S2C resolve_events + snapshot
```

`draw_reveal_and_plan_begin` 必须来自同一个原子事务，并携带 `transition_id`、`round_id`、新的 `plan_phase_revision`、揭示后的 `public_state_revision` 与服务器绝对 `plan_deadline`。客户端应用该公共版本前不能开放规划输入，也不能用本地收包时间自行重算截止时间。

所有客户端命令至少携带 `round_id / phase_revision / command_id / seat_epoch`；其余字段按命令携带：

```text
round_id
phase_revision
command_id
seat_epoch
offer_id       OFFERED 后的抽取操作
candidate_handle / controller_handle
```

- `draw_open` 不带 `offer_id`，由服务器生成；`NO_CANDIDATES / AVAILABLE` 状态直接 `draw_pass` 也不带 `offer_id`。
- `OFFERED` 状态的 `draw_pick / draw_pass` 必须带 `offer_id`；`draw_pick` 还必须带候选 `candidate_handle`。
- 每条入站命令先验证当前 `active_connection_id + seat_epoch`；幂等结果按 `(match_id, seat, command_id)` 保存，重连不能让同一逻辑命令执行第二次。
- 相同 `command_id` 重试返回原结果，不能重复选取、生成、销毁、转移、扣费或扣耐久。
- 旧回合、旧阶段、旧 `offer_id`、不属于该 `offer_id` 的候选句柄和伪造位置全部拒绝。
- 私密打开与私密选择只推动本人的 `private_draw_revision`，不能改变对手可见的 `public_state_revision`；公共状态只在 `draw_reveal_and_plan_begin` 的原子节拍变化。
- 权威回放必须区分 `ITEM_USED`、`ITEM_EFFECT_REPLAYED`、`ITEM_INSTANCE_CREATED`、`ITEM_INSTANCE_MOVED`、`ITEM_DEPLETED` 与 `SLOT_VACATED`。

## 13. 必测边界

### 取得与信息

- 开局三框全空，第 1 回合取得的 `0` 费道具也只能第 2 回合使用。
- `N=0 / 1 / 2 / 3 / 4` 时候选数严格等于 `min(3, N)`。
- 同名不同 UID 可以同时出现，选择一件不修改另一件耐久或位置。
- 关闭、重复打开、重发与重连均恢复同一候选句柄和顺序；服务器内部另行断言其映射的 `asset_uid` 不变。
- `AVAILABLE` 可以直接放弃且从未生成 `offer_id`；未打开直到超时也不能推进候选随机流。
- 双方不同操作速度下只收到同一批 `draw_reveal_and_plan_begin`，行动计时从该原子跃迁后开始。
- `draw_reveal_and_plan_begin` 的公共版本、阶段与截止时间不可拆分；乱序、丢包和跃迁中重连都不能先开放规划再补公开结果。
- 只要任一方有公开空框就进入抽取阶段；私密 `NO_CANDIDATES` 不能触发提前跳过，另一方无法由阶段是否出现推断背包余量。
- `PICKED` 到揭示前，公共框与对手快照保持原样。
- 对手不能区分主动放弃、超时和没有候选。
- 多组固定种子验证所有合法 UID 等概率，英雄、稀有度、同名与耐久都不改变单 UID 权重。
- 客户端即使读取全部公开 BattleCore RNG 状态，也不能预测本人或对手下一轮候选。
- 小背包、重复件和单件高价道具按背包总件数 / 价值分别统计候选率与胜率。

### 框位、费用与耐久

- 耐久扣至 0 后效果完整结算，但本轮不能再使用或普通填框。
- `slot_vacated` 只在最终清理产生一次，下一回合抽取能看见新空框。
- 多耐久件按 `READY → USED_THIS_ROUND → START_(R+1) → READY` 转移，移动后已使用记录仍跟随实例。
- 正常移动出的存活实例立即腾框，后续明确生成 / 移动效果可以按顺序利用。
- 原子拒绝的序列不扣费、不扣耐久、不腾框。
- 比赛结束仍正确落账残损与耗尽资产。

### 断线与幂等

- 在 `AVAILABLE / OFFERED / PICKED / PLAN / RESOLVE` 分别断线重连，阶段和截止时间均不重置。
- 抽取超时放弃，行动超时提交“攒”；已提交序列保持不变。
- 反复上下线不刷新 30 秒席位保留时间，新连接接管后旧连接命令失效。
- 截止时刻到达的命令按 `received_at <= deadline` 接受；同批到期、正常终局与旧连接入队命令按本文固定优先级得到一致结果。
- 重连后的 `seat_epoch` 会拒绝旧连接尚未处理的包，同时保留原命令的幂等回执。
- 从事件游标续播不重复动画、扣费、扣耐久或生成实例。
- 对手快照永远不含私密候选。

### 实例与归属

- 任一存活 UID 恰好位于一个容器，快照、交换、生成、销毁后都不重复。
- 己方交换保留可用状态；跨方整体交换保留资产归属并锁到下回合。
- 双方同时整体交换按奇偶结算，不依赖玩家编号。
- 整体交换分别覆盖空框、锁定件、已用件和待销毁框；剩余 1 / 2 耐久的交换件都不会复活或丢失 UID。
- 复制效果不产生新 UID，不再次消耗原实例，也不递归触发“使用道具”。
- 来源被动态完全反制时，复制件消耗但收益为 0，且不能回退复制更早的道具。
- 复制实体生成新 UID、继承当前耐久、标记为本场临时并锁一回合。
- Run 临时与本场临时在战末、搜刮和撤离时分别得到正确处理。
- 对方控制的本场临时件战末直接删除，不触发归还或临时战备；任何移动、交换和复制都不能延长临时生命周期。
- 搜刮改变原 `REAL` UID 的资产归属，败者替代件使用另一个全新 `RUN_TEMPORARY` UID，二者不能重复或互相覆盖。
- 主动销毁后再使用同一 UID 的序列整体拒绝。
- 战后先按资产归属归还，只有正常搜刮能改变真实资产所有权。

## 14. 明确不采用

- 随机或指定起手道具；
- 不足 3 件时禁止抽取、补系统假道具或对同一 UID 有放回补满；
- 按名称去重候选；
- 把抽取夹在行动倒计时中，或先点击者先看见公开结果；
- 耐久归零后在同轮默认立刻补抽 / 普通填框；
- 抽取超时随机替玩家选择；
- 断线无限冻结或每次重连刷新倒计时；
- 战斗内交换直接改变永久资产所有权；
- 复制效果时再次消耗原件，或复制实体时凭空生成可撤离资产；
- Demo 通用单件偷取与免费弃置真实道具；
- 用玩家编号、客户端到包顺序或动画先后裁定跨方实例冲突。

## 15. 当前实现迁移差距

当前运行时已有真实背包 UID、固定候选和私密快照的部分骨架，可以沿用思想；但以下行为仍属于旧实现：

- `STARTER_ITEM_IDS` 与旧槽位自动解锁；
- 只有 `SELECT / DEATH_SWITCH / OVER` 的相位模型，没有独立 `DRAW / DRAW_REVEAL / PLAN`；
- 断线通过不断顺延 deadline 暂停，尚未采用“不停钟 + 30 秒席位保留”；
- 实例只含简化的 `{uid, item_id, temporary}`，缺少完整耐久、生命周期、资产归属与当前控制；
- 旧槽字典交换、一次性清槽和旧复制路径尚未按 UID 单一真相重写；
- AI、UI、协议、回放、快照、存档和规则测试均未迁移到本文状态机。

因此任务 1 的完成含义是**规则边界已经封板**，不是运行时代码已经完成。
