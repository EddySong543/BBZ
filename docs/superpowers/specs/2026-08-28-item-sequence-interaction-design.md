# 道具有序施放与联机提交设计

> **状态：已确认。** 拖拽区域、松手后的撤销 / 重排方式等 UI 细节留待单独讨论。
> **当前规则入口：**取得、锁定、逐次使用费和冲突裁定以 [`2026-08-30-item-system-current-standard.md`](2026-08-30-item-system-current-standard.md) 为准；本文只负责有序施放与联机提交。
> **跨玩家结算：**双方唯一主行动固定在共同 `0` 拍、其余步骤保留相对顺序，以 [`2026-09-03-action-anchor-sequence-design.md`](2026-09-03-action-anchor-sequence-design.md) 为准。旧 H03 左对齐方案仅保留历史审计价值。

## 目标

让道具的操作感来自真实结算顺序：同一组道具与行动按不同顺序使用，能够自然形成不同局面。顺序差异必须来自状态已经发生改变，而不是在文案中硬写“若在攻击前/后使用”。

本文件只固定机制与联机边界，不改现有道具目录，也不实现拖拽 UI。逐次使用费、耐久、占格和金币已在后续阶段收口，见 [`2026-08-30-item-four-axis-balance-design.md`](2026-08-30-item-four-axis-balance-design.md)；该文件正文现为五维基准。

## 设计原则

1. 道具在权威序列轮到自身步骤时立即结算；后续步骤读取已经改变的真实状态。本地松手只追加步骤，不提前生成权威结果。
2. 效果默认只影响其结算后的事件，不追溯此前已经完成的步骤，因此玩家文案无需补“此后”。
3. 好顺序应是局面选择，不是唯一正确答案。`A → B` 与 `B → A` 应至少在一部分合理局面中各有用途。
4. 不用“若本回合已攻击”“若在攻击前使用”一类分支替顺序制造差异；没有状态变化、只有条件判定的顺序题属于伪设计。
5. 不把明显亏损的误操作包装成博弈。例如先用会完全浪费、后用永远更赚，只是知识检查。

## 已确认的正反例

以下效果是后续重设计的机制样板，最终稀有度与数值仍需随整池校准：

- **破魔矢·重设计**：`我方下一次「波」的总伤害增加1点并穿防。` 动作前使用可强化本次攻击；动作后使用则把公开威胁留给下一次攻击。两种顺序改变真实状态与对手决策。
- **蜕毒蛊**：`将敌方出战英雄的全部毒素移给生命最低的另一名存活敌方英雄。` 先转移再施毒、先施毒再转移，以及引爆前后的使用，都会形成不同的毒素分布和击杀线。
- **回声符**：`再次结算我方上一件使用的 T1 道具。` 它复制实际的上一道步骤，只能复制 T1，不能复制自己或 T2/T3；放置位置直接决定复制对象。

以下结构不再采用：

- 噬铁虫、回锋鞘通过“攻击前/攻击后”条件分支硬造两种效果。
- 魔晶与坩埚一类只有一个固定最优顺序、另一顺序等同浪费的组合。

## 拖拽释放语义

采用“本地编排、最终整体提交”的交互方案：

1. 玩家按住左键把道具拖出槽位时，只进入拖拽预览；只要没有松开左键，道具就没有释放，不消耗，也不进入待提交序列。
2. 玩家在合法释放区域松开左键时，视为释放该道具：立刻播放本地施放动画，并把这次道具使用追加到本回合的本地待提交序列。
3. 玩家随后可以继续释放道具或选择行动，界面按实际操作顺序记录完整步骤，例如 `[道具 A, 行动, 道具 B]`。
4. 点击本回合最终确认后，客户端一次性提交完整有序序列；确认前不把步骤逐条公开给对手。
5. 松手后的撤销、重排、非法区域回弹、目标选择手势和确认按钮的具体表现留给后续 UI 设计。本文件不预设允许或禁止撤销。

“松手播放动画”与“公开结算动画”是两层反馈：前者只在本地表现玩家已经完成一次编排；后者在双方提交、服务器权威结算后，依据服务器事件流向双方播放。前者不能提前泄露给对手，也不能作为结算真相。

## 联机权威模型

- 客户端在确认前只保存私有待提交序列；网络到达顺序不得成为战斗先后手。
- 最终提交至少携带回合号、按顺序排列的步骤，以及每个步骤需要的道具来源槽、行动、目标和附加选择。
- 服务器在权威 BattleCore 的克隆上校验并重放整段序列，包括回合合法性、槽位归属、重复使用、目标、逐步剩余能量和状态依赖。任一步非法时整段拒绝，不能只执行合法前缀。
- 每个道具步骤固定执行：检查当前能量与合法性 → 支付该道具本次使用费 → 扣 1 耐久 → 结算效果。前件产出的能量可以支付后件，后件不能倒付前件。
- 只有权威重放产生“道具已使用”事件才支付费用并扣耐久；整段拒绝、拖拽预览和本地撤销都不扣。合法使用即使被反制、免疫或收益为 0 仍支付并扣耐久。同一实例每回合最多使用一次，限制绑定实例 ID。
- 双方合法提交后，服务器先定位各自唯一主行动并将其固定在共同 `0` 拍；主行动前后的步骤保持与主行动的距离和原顺序，缺位处由服务器生成无费用、无触发的对齐等待。同拍两方已经开始的步骤均完成，不能由内部遍历顺序制造先手。列结束后的权威效果仍可在下一真实步骤前生成额外等待；两类等待都不是客户端可提交的步骤。随后服务器广播权威事件流与快照，客户端只用它驱动公开战斗动画和最终状态。
- 断线重连、超时默认行动和序列版本兼容继续沿用服务器权威原则，具体协议升级在实现阶段另写技术计划。

## 与当前实现的差距

新版单机道具路径已经使用统一有序步骤与行动锚点调度器。旧 BattleCore、未来网络协议及各表现入口仍须以行动锚点真相源逐项审计；H03 的旧延后实现只作迁移期兼容，不能反向定义当前英雄设计。

因此后续实现不能只给现有数组加拖拽外观，而应把本回合意图升级为统一的有序步骤结构，并同步 BattleCore、AI、网络协议、回放/快照与 UI 预览。

## 后续验收门槛

- 按住拖出但未松手时，道具状态与待提交序列均不变化。
- 一次合法松手只追加一个步骤、只播放一次本地施放反馈。
- 不同拖放顺序能稳定序列化，并在本地、服务器和回放中得到同一结果。
- `[道具, 波]` 对 `[防]` 时，波与防必须同在 `0` 拍，前置道具数量不能使防御落空。
- 对手在双方最终确认前看不到待提交步骤及其顺序。
- 服务器能原子拒绝重复槽、非法目标、过期回合和中途失效的序列。
- 重复提交不能重复扣耐久；复制道具效果只消耗复制件，不再次消耗原实例。
- 两个客户端收到一致的权威事件流与快照，公开动画不依赖任一客户端的本地预演。
- 道具内容审查必须证明顺序差异来自真实状态变化，并排除硬编码 if/else 与唯一最优顺序。
