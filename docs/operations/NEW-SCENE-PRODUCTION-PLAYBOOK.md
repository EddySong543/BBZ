# BBZ 新战斗场景制作手册

本手册来自 Scene2 的完整制作与返工记录。目标不是限制美术风格，而是把已经验证有效的工程边界、制作顺序和验收方法固化下来，让后续场景把时间用于设计，而不是重复排查场景覆盖、素材漂移、动效穿帮和运行预览不一致。

## 1. 不可破坏的基础契约

新场景只负责场景特有的美术、层级、材质和参数。以下内容默认从成熟 Battle Screen 直接复用：

- UI、人物尺寸与站位逻辑；
- 鼠标移动分层、镜头与输入；
- 回合计时、按钮状态、头像切换、死亡换人等战斗交互；
- 角色像素过滤、动画和倒影接口；
- 已验证的性能探针与测试入口。

新场景必须拥有独立可运行入口。复用基础场景不等于替换旧场景，Scene1 的正式入口不得因 Scene2/Scene3 开发而改变。编辑器 F6 与运行入口不一致时，先检查场景继承、实例引用和运行目标，不要复制第二套战斗逻辑。

## 2. 正确的制作顺序

### 阶段 A：先锁定构图骨架

在精修素材前只确定五个锚点：

1. 角色站立基线；
2. 战斗平台顶面；
3. 前景水线或地面边界；
4. 主视觉的大体量与方向；
5. 远、中、近景的遮挡顺序。

角色位置是硬约束。桥、地面和水面应围绕角色基线调整，不能先把背景摆漂亮，再移动角色补救。先用纯色块或低纹理素材验证剪影、留白和视线流向；这一步未通过，不进入滤镜与动效。

### 阶段 B：逐层接入成熟资产

推荐顺序：

1. 天空与最远景；
2. 远山；
3. 中山与主视觉承托结构；
4. 战斗平台；
5. 前景水面或地面；
6. 左右装饰；
7. 云雾、瀑布、粒子等动态层。

每次只接入一类资产，先处理尺寸、位置、遮挡和像素密度，再做颜色。素材应是可组合的单体资产，不是带完整天空、地面和构图的小海报。瀑布、云、树枝等需要运动的部分尽量与静态山体分离。

### 阶段 C：材质与色彩统一

先检查灰阶关系，再检查色相：

- 前、中、后景必须能在灰阶下分开；
- 近景不能因“融合”而变灰、变糊；
- 远景可降低对比和纹理，但不能透明穿帮；
- 同一层的独立山体需要独立 Material，不能因共享资源导致一调全调；
- 优先用现有亮度、对比、饱和度和色调参数微调，不为小问题增加全屏 Shader。

Material 是渲染参数集合，不等同于必须增加滤镜。能用节点参数解决的色彩问题，不新增每像素计算。角色保留原始像素、饱和度、暗部层次和面部可读性，环境光只做克制的补光与接触关系。

### 阶段 D：动效与环境生命感

动效按主次分配速度：

- 主动效：瀑布、核心机关或主视觉；
- 次动效：河面、云雾、树枝；
- 氛围动效：粒子、花瓣、尘点。

不同系统不能同速、同相位、同频率持续运动。主干、建筑和山体保持稳定，只让有物理理由的局部运动。树枝摆动必须使用局部遮罩，并为裁切连接处准备同色补图；补树干用树干色，补花朵用花朵色。

云雾需要连续覆盖但仍能辨认独立云团。使用稳定随机种子生成形状，避免同形重复；检查循环接缝、单像素尖柱和中间空洞。顶部云可以更快，底部云更厚更慢，并通过相反方向的叠层形成缭绕感。

粒子优先复用成熟场景的视觉语言，只改方向、颜色、数量和速度。先保证肉眼可辨，再控制密度；小到像坏点、过度旋转或大面积持续出现都会增加视觉疲劳。

## 3. 瀑布专项标准

瀑布必须先作为山体结构的一部分成立，再作为动画成立：

- 水源、跌水沿、主体水流、入水口和水面扩散缺一不可；
- 主轮廓以垂直边和少量清楚的像素台阶为主，避免平滑斜切或粗大裁剪块；
- 上下段错位时需要真实承托台阶和会动的跌水沿，不能让水流凭空转向；
- 高光沿水流方向纵向组织，横向只做间歇连接；
- 水花错峰出现和消散，入水口可用较连续的白色区域，水面波纹更慢；
- 颜色控制在清楚的暗、中、亮层级，避免过多波光同时竞争；
- 裁剪后逐像素检查山水接缝、循环首尾、闪烁直角和单像素空洞。

当一个视觉问题连续两轮仍没有被准确修复时，停止盲改：截出明确区域，与用户确认异常点，再查找专业教程或成熟游戏案例后实施。

## 4. 光线、阴影与视觉焦点

亮场景不等于所有元素都亮。优先级应为：

1. 人物与关键 UI；
2. 主视觉、战斗平台和主要装饰；
3. 远山、天空、前景水面和氛围粒子。

统一使用方向一致的轻量阴影帮助 UI 从明暗背景中分离。阴影应贴合控件轮廓，偏移以向下为主，不能变成四周黑描边或模糊矩形底板。小控件比按钮更轻，头像框比底部按钮更贴近主体。

静态光负责建立受光面、背光面与接触阴影；动态光只在确有构图价值时加入。树叶间歇漏光可作为后期加分项，但不得依赖大面积灰白蒙版伪造光照。任何全屏效果都要同时检查角色清晰度和帧时间。

## 5. 性能与工程边界

- 不为参数可以解决的问题新增全屏或高频 Shader；
- 不复制战斗逻辑，不在新场景创建第二套 UI 与角色系统；
- 静态节点尽量留在 `.tscn`，脚本负责数据、状态和动画；
- 共享材质用于确实要同步的对象，独立调整对象使用独立材质；
- 粒子总量、Shader 分支和动态重绘同时纳入性能探针；
- 引擎导入、测试和截图统一通过 `tools/run_godot.ps1`，不关闭用户手动打开的 Godot。

## 6. 测试与验收纪律

测试保护行为和语义，不把会频繁手调的位置、大小、透明度写死：

- 可以测试“Scene1/Scene2 是独立入口”“顶部云快于底部云”“阴影位于主体后方”；
- 不应测试“某座山必须位于固定坐标”“素材透明度必须等于某个临时数值”；
- 大改动跑全量 GUT，小型参数微调只跑必要测试；
- 视觉完成至少检查一次真实运行截图；遮罩、透明边、接缝和层级不能只看代码；
- 新场景同时检查旧场景回归，但只检查受共享代码影响的必要项目；
- 性能改动使用探针记录帧时间、draw calls 和对象数，不凭电脑风扇判断根因。

## 7. 下一场景启动清单

### 开工前

- [ ] 新建独立场景入口，不替换已有正式场景；
- [ ] 直接实例化成熟 Battle Screen 基础结构；
- [ ] 确认角色位置、平台顶面和水线/地面线；
- [ ] 确认主视觉方向、非对称构图和 UI 留白；
- [ ] 列出需要独立生成的单体素材与动态拆分。

### 美术接入

- [ ] 统一命名、目录和 nearest 像素过滤；
- [ ] 先尺寸与层级，后颜色与 Material；
- [ ] 灰阶检查前中后景；
- [ ] 检查素材白边、黑边、透明洞和像素密度；
- [ ] 动态部分与静态承托结构分离。

### 动效与收尾

- [ ] 主、次、氛围动效速度错开；
- [ ] 循环首尾无跳变、无单像素尖柱；
- [ ] 角色、平台和环境存在接触关系；
- [ ] UI 在暗/亮背景中均清晰，阴影不抢眼；
- [ ] 粒子肉眼可辨但不持续铺满画面；
- [ ] Scene1/新场景截图、必要交互、全量 GUT 和性能探针通过。

遵循这套顺序时，用户手动微调位置和尺寸不会破坏测试，新场景也不会因为复用错误而改变旧场景。后续迭代应优先调整可暴露参数，只有结构性问题才修改资产、节点层级或 Shader。
