# 英雄设计协作经验与提交前门禁

> 更新：2026-08-27
> 用途：沉淀 h01—h24 重设计过程中反复验证的经验，作为后续英雄机制、技能命名、技能图标、玩家文案与实装工作的统一提交前门禁。
> 关系：本文件总结“如何工作与如何自检”；机制分类以 `heroes-schools.md` 为准，玩家文案以 `copy-style-guide.md` 为准，已批准英雄以 `heroes.md` 与对应资源为准，命名素材以 `naming-bank.md` 为准。

---

## 1. 总原则

1. **Eddy 负责定设计，Codex 负责提出可评审方案并准确实装。** 一旦机制、数值、文案或名称获批，不擅自追加平衡尾巴、保护条件或“优化”。
2. **机制成立与数值平衡分开处理。** 重设计阶段优先判断是否好玩、是否产生选择和组合；只有明确要求强度评审时才讨论数值。单一英雄的原始胜率会被阵容、出场时机、使用率和玩家水平混杂，不能直接作为机制优劣结论。
3. **英雄是底层规则改装件。** 优先改写「波 / 攒 / 防 / 大波 / 大防 / 切换 / 行动 / 阵位 / 共享能量 / 生命」之间的关系，不为一名英雄另建小游戏。
4. **简单不是少写几个字。** 合格的简单是“一条规则开放很多用法”；把复杂想法缩成四字、把条件藏进术语、或把多个例外塞进一句话，都不是真正简化。
5. **保持独立判断。** Eddy 的质疑是需要重新审查的设计问题，不是自动同意的指令。回答应说明真实收益、风险和边界；若原方案仍更好，应给出理由。

## 2. 英雄机制设计

### 2.1 正确起点

按以下顺序推导：

```text
动物与角色形象
→ 战斗动作、动画或作品中的可视化灵感
→ 能力会怎样改写波波攒底层选择
→ 一句技能规则
→ 队伍组合与对手反制
→ 最后才归入进攻 / 防守 / 经济 / 调度 / 控制
```

- 动物联系必须自然存在，但不能死抓生肖字面。羊可以通向祭司，马可以通向自由移动，狗可以通向追猎或侵蚀；不必每个技能都直接出现角、蹄、爪或叫声。
- 可以从动画、漫画、影视和其他游戏汲取“动作结构”和“力量感觉”，但不得抄袭或改写现成技能。
- 定位用于复盘，不用于填人数。不能因为“还缺一个防守英雄”就倒推一个防守模板。

### 2.2 合格机制的五项检查

每个候选至少回答：

1. **新增什么选择？** 玩家会因此改变哪次「波 / 攒 / 防 / 切换」或资源支付？
2. **怎样形成宽 combo？** 至少列出两个不同英雄或道具接口，并说明组合后新增的行动路线；“数值更高”“大家都受益”不算。
3. **对手怎样应对？** 对手应能改变目标、行动、资源时机或阵位，而不是只能接受自动收益。
4. **是否能一句话读懂？** 核心技能应只有一个明显规则变化；完整边界可以写进设计说明和测试，不塞进英雄小字。
5. **UI 能否自然承载？** 若必须新增多个头像标记、隐藏计数、特殊目标层或长说明，机制大概率过重。

### 2.3 反复失败的机制类型

以下方案在 h01—h24 过程中已反复被否决，不能换英雄或换关键词后再次提交：

- **动作对照表式 if–else**：敌方出 X，我方自动变 Y。它只是在结算后领奖，没有主动铺垫或兑现路线。
- **复杂 if–else**：简单条件不够有趣后继续叠第二条件、持续时间和例外，只会让小字变长，不会增加健康深度。
- **旧方案换关键词**：把以前的「波」改成「大波」、把「能量」改成「生命」、把触发对象换成另一英雄，不构成新设计。
- **只扫描当前英雄历史**：撞车检查必须覆盖整个 h01—h24 对话中的已采用方案和已否决骨架，不能只看当前编号。
- **路径依赖**：反复回到登场、离场、切换、命中加值、成功防御领奖等已经拥挤的结构。
- **孤立机制**：技能只提高自己一次伤害、回复或换血，队友只能旁观，不能生产、转交或兑现其结果。
- **指定体系队**：只有与唯一搭档同队才工作。体系成员可以存在，但接口必须对多个英雄或道具开放。
- **后台收租**：玩家不改变行动，技能自动持续给伤害、治疗或能量。
- **关键词伪设计**：为一个普通效果命名后便当作新系统，或要求其他内容专门服务该关键词。
- **超模式全能例外**：既免除支付、又增加行动、又提供伤害或防御，使英雄成为绝对核心而挤压队伍选择。
- **没有现场影响的空过**：准备动作既不改变当前盘面，也没有足够宽的未来兑现口。
- **UI 不可读的聪明点子**：机制有趣但需要额外选择层、隐藏状态或复杂历史记录时，优先简化或转为道具，不硬塞给英雄。

### 2.4 候选方案的最低差异

- 每轮至少提供 3 个真正不同的方向。
- “不同”要体现在触发、支付、产物、结算或玩家决策中的至少两项，而不是只替换名词。
- 汇报前先做全局撞车表：**已采用骨架 / 已否决骨架 / 本轮新骨架**。
- 如果三案最终都归结为“满足条件后加一点数值”，这一轮应整体推翻，不交给 Eddy 筛。

## 3. 技能命名

### 3.1 目标感觉

技能名应当：

- 脱离解释后仍像一个可以正式施展的**技能专名**；
- 保留适度东方幻想感，但不过度古风、道教化、佛教化、武侠化，也不滑向科幻或现代漫画口号；
- 与角色形象或能力方向存在可感知联系，但不直接复述规则；
- 通过一个自然的“幻想因果”成立，例如异境可以抵达、山河可以借骨、白额可以生出雷音、十方可以失去次第；
- 使用常见、可自然断句的词，不让解释承担修复语法的工作。

正向锚点包括：`步虚无有乡`、`玄金不动相`、`白额雷音`、`十方无次第`、`龙御极`、`神打`、`千里自在风`、`不坠神言`、`太初万法剑`、`影狩`、`暗潮`、`天不葬`、`七杀战鬼`、`白虹`、`同源万化妄真身`、`游丝引`、`天光长蚀`。

这些名字的共同点不是字词相似，而是各自拥有清楚的本体、唯一断句和角色尺度。

### 3.2 强制输出规则

- 每轮默认给 10 个候选，按推荐度从高到低排列。
- 候选覆盖 2—7 字，但不能为了凑字数给弱名字加尾巴。
- 每个候选附一条简短解释：解释意象来源和角色联系，不解释语法，不补救名字。
- 同轮不得反复使用同一模板、尾缀或词群，如多个「××令」「××战法」「××之术」。一个模板被否定时，不应拖垮半轮方案。
- 先生成较大的内部草案池，再按下列淘汰表自检；不要把明显不合格的十个原始草稿直接交给 Eddy。

### 3.3 命名淘汰表

出现任一项即淘汰：

- 像说书标题、章节名、故事梗概、对白、谚语、格言或成语。
- 像道具名：尤其以一个具体器物收尾，而整体又没有明确施展动作。
- 像规则描述：只是把“命中后削能”“防住后强化”换成古词、倒装或缩写。
- 像词语拼盘：几个好听、宏大或阴暗的字并列，却没有自然语法和幻想因果。
- 像普通武侠招式：只靠拳、掌、手、劲、爪、战法、行军令制造技能感。
- 过度宗教化：佛、经、阎罗、轮回、金刚、天罗等只能少量使用；角色仅有宗教视觉元素时，不能让整轮都变成佛教词库。
- 过度诗意：读起来像诗句截取，却看不出是技能。
- 过度直白、太短或太普通：只有一个状态词、动作词或常见组合。
- 生僻到玩家不认识，或有两个同样自然的断句。
- 依赖「法 / 术 / 诀 / 印 / 神通」等后缀才像技能。
- 反复滥用「身 / 形 / 契 / 万钧」等已多次造成模板感的字。
- 把用户给出的优秀例子改一两个字后重新提交；只能学习命名方式，不能仿写。

### 3.4 h09 最近一轮的失败复盘

2026-08-26 的 h09 候选本应在汇报前被全部或大部淘汰：

- `一爪荒年`、`六爪无余`：仍是“爪击之后资源枯竭”的描述句，只是绕了一层。
- `金刚坏`、`破戒杀生相`：重新把整轮拉回 Eddy 已明确要求降低的佛教方向。
- `回风惊神`、`六爪摧锋散手`、`天河倒悬截流手`：武侠动作与宏大词堆叠，AI 组合痕迹明显。
- `熄星`：过于简单、普通，无法单独建立 h09 的技能身份。
- `猿臂横江`：更像成语化的力量描述，且重新死抓猴的肢体特征。

该轮的根因不是“词还不够好”，而是没有先确定 h09 的独有力量本体，就急着围绕“爪 + 削能”造句。后续重命名应先回答：**紫火究竟以什么奇幻力量让敌方的行动余力随伤害一同消失？** 确定本体后再命名，不能继续从爪、佛教或能量枯竭三个词群机械组合。

## 4. 技能图标与 PixelLab Prompt

### 4.1 核心原则

技能图标的优先级是：

```text
缩略尺寸下能看懂
> 能表现技能机制
> 与技能名或角色意象有联系
> 诗意与隐喻
```

- 先研究成熟游戏图标如何用一个主体表达动作，再选择 hXX 的意象；不能只抓技能名做抽象图形。
- 使用**一个明确主体 + 一个必要反应**。例如力量被击碎、屏障留下、能量弧远去；不要把角色、场景、文字、特效和多个物件全部塞进去。
- 主体必须是绘图模型能直接理解的具体视觉对象或现象，不能用“空间被控制”“黑暗转化为一切”这种概念句直接当 prompt。
- 图标在很小尺寸下要有清楚轮廓、中心构图、有限配色和明确明暗层级。

### 4.2 已确认的负面规则

- 默认避免小人、完整人物、明确人物形象、身体剪影和动物头；不要让 AI 把能量形状理解成彩色小人。
- 默认避免只画身体局部；只有动作本体无法脱离肢体时才例外，并应尽量物件化或能量化。
- 不反复使用剑。只有 h10 这种技能本体就是剑时才使用剑阵或剑影。
- 不用孤立几何图形冒充深意；抽象形状必须能立刻对应一个可读动作。
- 不使用猪头、嘴加能量、狗头等头像式设计作为技能图标。
- 避免黑色主体叠多种高饱和颜色，容易显脏并失去轮廓。
- 避免无关的 splash、背景曲线、装饰飘带、复杂法阵和大量碎屑。
- 不偷用现成能量点、美术资产或 UI 框作为新技能图标主体。
- 名称包含“神言”不意味着必须画清晰文字；需要文字时让文字构成主要形状，并避免要求模型生成可读具体汉字。

### 4.3 Prompt 写法

- 默认使用英文、纯视觉描述。
- 先写主体，再写动作或变化，再写材质和配色，最后写必要的负面约束。
- 描述画面中真实可见的内容，不写机制解释、世界观说明或抽象情绪长句。
- 三方案必须更换**主要视觉主体或构图逻辑**，不能只是同一图案换颜色。
- 不主动写画布尺寸、`pixels`、`true pixel`、抗锯齿或采样参数；只在 Eddy 明确要求特定工具参数时补充。

建议骨架：

```text
A centered fantasy game skill icon showing [one clear subject],
[one visible action or transformation], [material and limited palette],
strong readable silhouette, clean focal point, isolated composition,
no character, no animal head, no text, no UI frame, no background splash.
```

具体技能需要人物、文字、武器或框体时，应逐项解除对应限制，而不是无差别套模板。

## 5. 玩家文案与术语

1. **技能小字只写核心规则。** 目标锁定、同拍换位、落空、道具例外、结算顺序等进入设计说明与测试。
2. **一句话包含谁、何时、发生什么。** 不用复杂从句，不把开发术语展示给玩家。
3. **状态词严格区分：**
   - `在场时`：当前位于作战位期间；
   - `在队时`：在队伍中存活即可，包括未出战；
   - `登场时`：切换到作战位的瞬间；
   - `未出战时`：位于场下。
4. **攻击只指英雄使用「波」或「大波」。** 独立主动技、道具伤害、追击、反击、毒素引爆等统一叫伤害。
5. 若技能依据「波 / 大波造成的实际伤害」计算，并需要把附在攻击上的道具加伤算入，应直接写「波」和「大波」，不能用含义更宽或更窄的简称蒙混。
6. **持续效果必须同时确定对象、范围、持续时间与清除节点。** 默认挂在单个英雄身上；全队效果必须明确写出。
7. 反复出现、可跨英雄或道具复用的效果才进入效果图鉴；只出现一次的机制用大白话。
8. 主动技能文案不重复 UI 已显示的能量、次数和上限；这些信息由按钮与标记承担。

## 6. 主动技能与 UI

- 主动技能若是某个基础行动的变体，应作为该行动旁边的**分支按钮**出现，而不是塞进结束按钮或藏成难以察觉的小角标。
- 分支按钮沿用现有行动按钮的形状、材质、边框和交互反馈；只缩小尺寸，不另造一套徽章语言。
- 费用标记放在分支按钮固定角落，技能图标必须视觉居中，尺寸、配色和留白与相邻行动按钮一致。
- 不能保留多余的暗色圆角背景，也不能拿能量点素材直接充当技能外框。
- 主动 / 被动标签、战斗按钮、英雄图鉴必须一致；不能只改战斗场景。
- UI 方案如果“不额外占空间但几乎看不见”，仍然是不合格方案。可发现性优先于形式上的极简。

## 7. 实装与全局同步

每次获批后先扫描一次英雄编号、旧技能名和旧文案的全部引用，再精确修改。至少检查：

- `assets/data/heroes/hXX.tres`：名称、类型、文案、图标路径等玩家数据；
- `src/battle/skills/`：技能实现、类名、注释与注册；
- 战斗结算和主动技能 UI：按钮位置、费用、触发时机、作用对象；
- 英雄图鉴：名称、主动 / 被动标签、说明与图标；
- `design/heroes.md`、`heroes-redesign.md`、`heroes-schools.md`：玩家快照、设计理据和定位；
- 单元测试、契约探针和可能硬编码的旧名称；
- 图标与动画资源路径、导入文件及正式归属目录。

执行纪律：

1. 不乱改成熟项目结构，不顺手清理无关代码。
2. 保留工作树中其他任务或用户已有改动，只处理本轮明确文件。
3. 不只更新战斗表现；数据、图鉴、文档、测试和 UI 均须同步。
4. 不用截图证明完成。通过 Godot 日志、单元测试、几何断言和资源引用检查验证。
5. 汇报只包含：改了什么、验证结果、仍待 Eddy 决定的事项；未获批候选不写成既定事实。
