1. **解析参数**，获取可选的类型/主题提示（如 `roguelike`、`space survival`、
   `cozy farming`）。若参数为 `open` 或无参数，则从零开始。同时解析审查模式
   （本次运行只解析一次，存下供所有评审关卡生成使用）：
   1. 若传入了 `--review [full|lean|solo]` → 使用该值
   2. 否则读取 `production/review-mode.txt` → 使用该值
   3. 否则 → 默认 `lean`

   完整检查模式参见 `.claude/docs/director-gates.md`。

2. **检查已有的概念工作**：
   - 若 `design/gdd/game-concept.md` 存在则读取（续作，不推倒重来）
   - 若 `design/gdd/game-pillars.md` 存在则读取（在已确立的支柱上继续构建）

3. **交互式地推进各构思阶段**，每个阶段都向用户提问。**不要**闷头默默生成
   一切——目标是**协作式探索**：AI 扮演创意引导者（Facilitator），而非替代
   人类愿景的角色。

   在整个头脑风暴过程中的关键决策点**使用 `AskUserQuestion`**：
   - 受限的品味问题（类型偏好、范围、团队规模）
   - 概念选择（展示选项后问"哪 2-3 个概念打动你？"）
   - 方向选择（"继续深化、再探索一些，还是做原型？"）
   - 概念细化后的支柱排序
   先在对话正文中写出完整的创意分析，再用 `AskUserQuestion` 以简洁的标签
   捕获决定。

   需要遵循的专业工作室头脑风暴原则：
   - 搁置评判——探索阶段没有坏点子
   - 鼓励不寻常的想法——跳出框架的思考能激发更好的概念
   - 互相叠加——用"对，而且……"回应，而不是"但是……"
   - 把约束当作创意燃料——限制往往产出最好的点子
   - 每个阶段设定时间盒（Time-box）——保持节奏，早期不过度斟酌

### 阶段 1：创意发现（Creative Discovery）

先理解这个人，而不是这款游戏。以对话方式（而非清单式）问这些问题：

**情感锚点**：
- 有没有某个游戏瞬间真正打动过你、让你兴奋，或让你忘记时间？具体是什么
  制造了那种感受？
- 有没有你一直想在游戏里体验、却从未真正找到的幻想或力量感？

**品味画像**：
- 你投入时间最多的 3 款游戏是什么？是什么让你不断回去玩？
  *（以纯文本提问——用户必须能自由输入具体游戏名。
  不要把这题放进带预设选项的 AskUserQuestion。）*
- 有没有你热爱的类型？回避的类型？为什么？
- 你更喜欢挑战你的游戏、让你放松的游戏、给你讲故事的游戏，
  还是让你自我表达的游戏？*（此题使用 `AskUserQuestion`——受限选择。）*

**现实约束**（在头脑风暴前先框定沙盒）。
将这些捆绑进一个多标签页（multi-tab）的 `AskUserQuestion`，标签名必须严格如下：
- 标签 "Experience"——"你最希望玩家获得哪种体验？"（挑战与精通 / 故事与发现 / 表达与创造 / 放松与心流）
- 标签 "Timeline"——"你现实的开发时间线是多久？"（数周 / 数月 / 1-2 年 / 多年）
- 标签 "Dev level"——"你处于开发旅程的哪个阶段？"（第一款游戏 / 发布过作品 / 专业背景）

必须使用完全一致的标签名——不要改名或重复。

**综合**这些回答，产出一份**创意简报（Creative Brief）**——用 3-5 句话总结
这个人的情感目标、品味画像和约束条件。把简报念回给用户，确认它准确捕捉了
其意图。

### 阶段 2：概念生成（Concept Generation）

以创意简报为基础，生成 **3 个各有不同创意方向的概念**。使用以下构思技巧：

**技巧 1：动词优先设计（Verb-First Design）**
从核心玩家动词出发（建造、战斗、探索、解谜、生存、创造、经营、发现），
由内向外构建。动词本身就是游戏。

**技巧 2：混搭法（Mashup Method）**
组合两个出人意料的元素：[类型 A] + [主题 B]。两者之间的张力构成独特卖点。
（例如"农场模拟 + 宇宙恐怖"、"roguelike + 恋爱模拟"、"城市建造 + 即时战斗"）

**技巧 3：体验优先设计（MDA 逆推）**
从期望的玩家情感出发（MDA 框架的美学目标：感官 sensation、幻想 fantasy、
叙事 narrative、挑战 challenge、社交 fellowship、发现 discovery、
表达 expression、服从 submission），逆推能产生该情感的动态（Dynamics）
与机制（Mechanics）。

每个概念展示以下内容：
- **暂定标题（Working Title）**
- **电梯演讲（Elevator Pitch）**（1-2 句——必须通过"10 秒测试"）
- **核心动词（Core Verb）**（玩家最高频的单一动作）
- **核心幻想（Core Fantasy）**（情感承诺）
- **独特卖点（Unique Hook）**（通过"而且还"测试："像 X，而且还有 Y"）
- **主导 MDA 美学**（哪种情感占主导？）
- **预估范围（Estimated Scope）**（小 / 中 / 大）
- **为什么可行**（1 句话说明市场/受众契合度）
- **最大风险（Biggest Risk）**（1 句话说明最难回答的未解问题）

三个概念全部展示。然后用 `AskUserQuestion` 捕获选择。

**关键**：这里必须是纯列表调用——不带 tabs、不带表单字段。严格使用以下结构：

```
AskUserQuestion(
  prompt: "哪个概念打动了你？可以选一个、组合多个概念的元素，或要求全新方向。",
  options: [
    "概念 1 —— [标题]",
    "概念 2 —— [标题]",
    "概念 3 —— [标题]",
    "组合多个概念的元素",
    "生成全新方向"
  ]
)
```

此处**不要**使用 `tabs` 字段。`tabs` 表单仅用于多字段输入——在这里用会导致
"Invalid tool parameters" 错误。这是一个纯 `prompt` + `options` 调用。

绝不施压催促选择——让用户慢慢消化。

### 阶段 3：核心循环设计（Core Loop Design）

针对选定的概念，用结构化提问构建核心循环（Core Loop）。核心循环是游戏跳动
的心脏——如果它单独拎出来不好玩，再多内容和打磨也救不了这款游戏。

**30 秒循环**（时刻层面·moment-to-moment）：

以 `AskUserQuestion` 提问——选项要从选定概念推导，不要硬编码：

1. **核心动作手感**——提问："核心动作的主要手感是什么？"生成 3-4 个符合该
   概念类型与调性的选项，外加一个自由输入的出口（`我来描述`）。

2. **关键设计维度**——找出对这个具体概念最重要的设计变量（如世界反应性、
   节奏、玩家能动性 Player Agency），围绕它提问。生成与概念匹配的选项。
   始终包含自由输入出口。

捕获回答后进行分析：这个动作本身是否令人满足？是什么让它有好手感？
（音频反馈、视觉爽感 Juice、时机满足感、战术深度？）

**5 分钟循环**（短期目标）：
- 什么把时刻层面的游玩组织成一个个周期？
- "再来一回合"/"再来一局"的心理在哪里被触发？
- 玩家在这个层面做哪些选择？

**单次会话循环**（30-120 分钟）：
- 一次完整的游玩会话是什么样子？
- 自然的停止点在哪里？
- 让玩家在不玩时还惦记这款游戏的"钩子"是什么？

**成长循环**（数天/数周）：
- 玩家如何成长？（力量？知识？选项？故事？）
- 长期目标是什么？游戏何时算"通关"？

**玩家动机分析**（基于自我决定理论 Self-Determination Theory）：
- **自主性（Autonomy）**：玩家有多少有意义的选择？
- **胜任感（Competence）**：玩家如何感受到自己技艺的成长？
- **归属感（Relatedness）**：玩家如何感到连接（与角色、其他玩家或世界）？

### 阶段 4：支柱与边界（Pillars and Boundaries）

游戏支柱（Game Pillars）是真实 3A 工作室（《战神》《哈迪斯》《最后生还者》）
用来让数百名团队成员的决策指向同一方向的工具。即使对独立开发者，支柱也能
防止范围蔓延（Scope Creep）、保持愿景锐利。

协作定义 **3-5 条支柱**：
- 每条支柱有一个**名称**和**一句话定义**
- 每条支柱有一个**设计测试**："如果我们在 X 和 Y 之间争论，
  这条支柱说我们选 __"
- 支柱之间应当彼此形成张力——如果所有支柱都指向同一方向，
  说明它们没发挥足够作用

然后定义 **3 条以上反支柱（Anti-pillars）**（这款游戏**不是**什么）：
- 反支柱防止最常见的范围蔓延："要是有……是不是很酷"这类不服务核心愿景的功能
- 表述为："我们**不做** [某事]，因为它会损害 [某支柱]"

**支柱确认**：展示完整支柱集后，使用 `AskUserQuestion`：
- 提问："这些支柱对你的游戏来说感觉对吗？"
- 选项：`[A] 锁定` / `[B] 重命名或重新表述某条` / `[C] 换掉某条支柱` / `[D] 其他`

若用户选 B、C 或 D，完成修订后再次使用 `AskUserQuestion`：
- 提问："支柱已更新。可以锁定了吗？"
- 选项：`[A] 锁定` / `[B] 再修订一条` / `[C] 其他`

重复直到用户选择 [A] 锁定。

**审查模式检查**——在生成 CD-PILLARS 与 AD-CONCEPT-VISUAL 前应用：
- `solo` → 两者都跳过。注明："CD-PILLARS 已跳过——Solo 模式。AD-CONCEPT-VISUAL 已跳过——Solo 模式。"直接进入阶段 5。
- `lean` → 两者都跳过（非 PHASE-GATE）。注明："CD-PILLARS 已跳过——Lean 模式。AD-CONCEPT-VISUAL 已跳过——Lean 模式。"直接进入阶段 5。
- `full` → 正常生成。

**支柱与反支柱达成一致后，在进入阶段 5 之前通过 Task 并行生成 `creative-director` 和 `art-director` 两个代理。两个 Task 调用必须同时发出——不要等一个完成再启动另一个。**

- **`creative-director`**——评审关卡 **CD-PILLARS**（`.claude/docs/director-gates.md`）
  传入：带设计测试的完整支柱集、反支柱、核心幻想、独特卖点。

- **`art-director`**——评审关卡 **AD-CONCEPT-VISUAL**（`.claude/docs/director-gates.md`）
  传入：游戏概念电梯演讲、带设计测试的完整支柱集、目标平台（如已知）、
  用户提到的任何参考游戏或视觉基准。

收齐两份判定后，用双标签页 `AskUserQuestion` 一并呈现：
- 标签 **"Pillars"**：呈现 creative-director 的反馈。选项沿用标准 CD-PILLARS
  处理方式——`按原样锁定` / `修订 [具体支柱]` / `进一步讨论`。
- 标签 **"Visual anchor"**：呈现 art-director 给出的 2-3 个命名视觉方向选项。
  选项：每个命名方向（一项一个）+ `组合多个方向的元素` + `我来描述自己的方向`。

用户选定的视觉锚（命名方向或其自定义描述）存为**视觉身份锚（Visual
Identity Anchor）**——它将写入游戏概念文档，并成为美术圣经（Art Bible）
的基础。

若 creative-director 对支柱返回 CONCERNS 或 REJECT，先解决支柱问题再请用户
选择视觉锚——视觉方向应当从已确认的支柱中生长出来。

### 阶段 5：玩家类型验证（Player Type Validation）

使用巴特尔分类法（Bartle Taxonomy）和 Quantic Foundry 动机模型，验证这款
游戏究竟是为谁做的：

- **主要玩家类型**：谁会**热爱**这款游戏？（成就者 Achievers、探索者
  Explorers、社交者 Socializers、竞争者 Competitors、创造者 Creators、
  故事家 Storytellers）
- **次级吸引力**：还有谁可能喜欢它？
- **这款游戏不适合谁**：明确谁不会喜欢这款游戏，与知道谁会喜欢同等重要
- **市场验证**：有没有服务类似玩家类型的成功游戏？从它们的受众规模能学到什么？

### 阶段 6：范围与可行性（Scope and Feasibility）

让概念落地现实：

- **目标平台**：使用 `AskUserQuestion`——"这款游戏瞄准哪些平台？"
  选项：`PC (Steam / Epic)` / `移动端 (iOS / Android)` / `主机` / `Web / 浏览器` / `多平台`
  记录答案——它直接影响引擎推荐，并将传给 `/setup-engine`。
  如有必要注明平台影响（例如移动端强烈倾向 Unity；主机上 Godot 有局限；
  Web 上 Godot 导出干净利落）。

- **引擎经验**：使用 `AskUserQuestion`——"你已经有惯用的引擎了吗？"
  选项：`Godot` / `Unity` / `Unreal Engine 5` / `没有偏好——帮我决定`
  - 若用户选定引擎 → 记录为其偏好并继续。**不要**质疑其选择。
  - 若选"没有偏好" → 告诉用户："本次会话结束后运行 `/setup-engine`——它会
    基于你的概念和平台目标带你走完完整决策。"此处不要给出推荐。
- **美术管线**：美术风格是什么？劳动强度多大？
- **内容范围**：估算关卡/区域数量、道具数量、游玩时长
- **MVP 定义**：能验证"核心循环好不好玩"的绝对最小构建是什么？
- **最大风险**：技术风险、设计风险、市场风险
- **范围分层（Scope Tiers）**：完整愿景是什么 vs. 时间耗尽时能发布什么？

**审查模式检查**——在生成 TD-FEASIBILITY 前应用：
- `solo` → 跳过。注明："TD-FEASIBILITY 已跳过——Solo 模式。"直接进入范围分层定义。
- `lean` → 跳过（非 PHASE-GATE）。注明："TD-FEASIBILITY 已跳过——Lean 模式。"直接进入范围分层定义。
- `full` → 正常生成。

**识别出最大技术风险后、定义范围分层前，通过 Task 生成 `technical-director`，使用评审关卡 TD-FEASIBILITY（`.claude/docs/director-gates.md`）。**

传入：核心循环描述、平台目标、引擎选择（或"未定"）、已识别的技术风险列表。

向用户呈现评估结果。若为 HIGH RISK，主动提出在定稿前重新审视范围。
若为 CONCERNS，记录并继续。

**审查模式检查**——在生成 PR-SCOPE 前应用：
- `solo` → 跳过。注明："PR-SCOPE 已跳过——Solo 模式。"直接进入文档生成。
- `lean` → 跳过（非 PHASE-GATE）。注明："PR-SCOPE 已跳过——Lean 模式。"直接进入文档生成。
- `full` → 正常生成。

**范围分层定义完成后，通过 Task 生成 `producer`，使用评审关卡 PR-SCOPE（`.claude/docs/director-gates.md`）。**

传入：完整愿景范围、MVP 定义、时间线估算、团队规模。

向用户呈现评估结果。若为 UNREALISTIC，主动提出在写文档前调整 MVP 定义或
范围分层。

4. **生成游戏概念文档**，使用 `.claude/docs/templates/game-concept.md` 模板。
   用头脑风暴对话内容填满**所有**章节，包括 MDA 分析、玩家动机画像和心流
   状态（Flow State）设计章节。

   **在游戏概念文档中包含"视觉身份锚"章节**，内容：
   - 选定的视觉方向名称
   - 一行视觉规则
   - 2-3 条支撑视觉原则及其设计测试
   - 色彩哲学摘要

   这一章节是美术圣经的种子——趁"一切必须动起来"之类的决定还没在会话之间
   被遗忘，先把它记录下来。

5. 使用 `AskUserQuestion` 请求写入批准：
- 提问："游戏概念已就绪。可以写入 `design/gdd/game-concept.md` 吗？"
- 选项：`[A] 可以——写入` / `[B] 还不行——先修订某章节`

若选 [B]：用 `AskUserQuestion` 询问要修订哪个章节，选项：`电梯演讲` /
`核心幻想与独特卖点` / `支柱` / `核心循环` / `MVP 定义` / `范围分层` /
`风险` / `其他——我来描述`

修订后，以 diff 或清晰的前后对照展示更新的章节，再用 `AskUserQuestion`——
"可以写入更新后的概念文档了吗？"
选项：`[A] 可以——写入` / `[B] 再修订一个章节`
重复直到用户选择 [A]。

若同意，使用 `.claude/docs/templates/game-concept.md` 模板生成文档，用头脑
风暴对话内容填满**所有**章节并写入文件，按需创建目录。

**范围一致性规则**：核心身份表中的"预估范围"字段必须与范围分层章节的完整
愿景时间线一致——不能只写"大型（9 个月以上）"。要写成"大型（X–Y 个月，
单人）"或"大型（X–Y 个月，N 人团队）"，让摘要表准确。

   步骤——不要缩略或截断：

**路径 A——设计优先**（概念已相当明确时推荐）：
   1. "运行 `/setup-engine` 配置引擎并填充版本感知的参考文档"
   2. "运行 `/art-bible` 创建视觉身份规范——在写 GDD **之前**做。**美术圣经是
      Technical Setup 关卡的前置要求。**它决定资产生产能否开始，并影响技术
      架构决策（渲染、VFX、UI 系统）。"
