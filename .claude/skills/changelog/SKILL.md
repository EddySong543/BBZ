## 阶段 1：解析参数

读取参数中的目标版本号或 Sprint 编号。若给出版本号，使用对应的 git 标签；
若给出 Sprint 编号，使用该 Sprint 的日期范围。

验证仓库已初始化：运行 `git rev-parse --is-inside-work-tree` 确认 git 可用。
若不是 git 仓库，告知用户并优雅中止。

---

## 阶段 2：收集变更数据

读取自上一个标签或发布以来的 git 日志：

```
git log --oneline [last-tag]..HEAD
```

若不存在标签，读取完整日志或一个合理的近期范围（最近 100 个提交）。

从 `production/sprints/` 读取相关时段的 Sprint 报告，了解计划中的工作和
变更背后的上下文。

从 `design/gdd/` 读取本时段内已实现新功能对应的已完成设计文档。

---

## 阶段 3：变更分类

将每项变更归入以下类别之一：

- **新功能（New Features）**：全新的游戏系统、模式或内容
- **改进（Improvements）**：对现有功能的增强、UX 改进、性能提升
- **缺陷修复（Bug Fixes）**：对损坏行为的修正
- **平衡性调整（Balance Changes）**：游戏数值、难度、经济的调优
- **已知问题（Known Issues）**：团队已知晓但尚未解决的问题
- **杂项（Miscellaneous）**：不属于上述类别的变更，或提交信息过于模糊
  而无法可靠归类的提交

对每个提交，检查其信息中是否包含任务 ID 或故事引用（如 `[STORY-123]`、
`TR-`、`#NNN` 或类似格式）。统计缺少任何任务引用的提交数量，并将该数量
写入阶段 4 的指标章节：`无任务引用的提交数：[N]`。

## 阶段 4：生成内部更新日志

```markdown
# 内部更新日志：[版本]
日期：[日期]
Sprint：[覆盖的 Sprint 编号]
提交数：[数量]（[first-hash]..[last-hash]）

## 新功能
- [功能名] —— [技术描述、受影响的系统]
  - 提交：[hash1]、[hash2]
  - 负责人：[实现者]
  - 设计文档：[链接（如适用）]

## 改进
- [改进项] —— [技术上改了什么、为什么]
  - 提交：[hashes]
  - 负责人：[谁]

## 缺陷修复
- [BUG-ID] [缺陷描述与根因]
  - 修复：[改动内容]
  - 提交：[hashes]
  - 负责人：[谁]

## 平衡性调整
- [调整项] —— [旧值 -> 新值] —— [设计意图]
  - 负责人：[谁]

## 技术债 / 重构
- [清理了什么、为什么]
  - 提交：[hashes]

## 杂项
- [不属于其他类别的变更，或提交信息模糊的提交]
  - 提交：[hashes]

## 已知问题
- [问题描述] —— [严重程度] —— [预计修复时间（如已知）]

## 指标
- 总提交数：[N]
- 变更文件数：[N]
- 新增行数：[N]
- 删除行数：[N]
- 无任务引用的提交数：[N]
```

## 阶段 5：生成面向玩家的更新日志

```markdown
# [版本] 更新内容

## 新功能
- **[功能名]**：[对玩家友好的描述——他们现在能做什么、为什么令人兴奋。
  聚焦体验，而非实现。]

## 改进
- **[改进了什么]**：[这如何让游戏对玩家更好。具体，但避免术语。]

## 缺陷修复
- 修复了 [描述玩家经历的现象，而非代码里哪儿坏了] 的问题
- 修复了 [玩家可见的症状]

## 平衡性调整
- [用玩家能理解的话说明改了什么及设计意图。
  示例："治疗药水现在恢复 50 HP（原为 30）——我们认为玩家在后期遭遇战中
  需要更多恢复手段。"]

## 已知问题
- 我们已注意到 [用玩家语言描述的问题]，正在修复中。[如有临时解决方案则说明。]

---
感谢游玩！你的反馈会让游戏变得更好。
问题反馈请至 [链接]。
```

---

## 阶段 6：输出

将两份更新日志都输出给用户。内部更新日志是主要工作文档；面向玩家的更新
日志经审核后即可用于社区发布。

---

## 阶段 7：提议写入文件

呈现更新日志后，询问用户：

> "可以把这份更新日志写入 `docs/CHANGELOG.md` 吗？
> [A] 可以，追加这条记录（若文件已存在则推荐）
> [B] 可以，整体覆盖文件
> [C] 不用——我手动复制"

- 询问前先检查 `docs/CHANGELOG.md` 是否存在。若存在，默认推荐 **[A] 追加**。
- 若用户选 [A]：将新的内部更新日志条目追加到现有文件顶部（最新条目在前）。
- 若用户选 [B]：用新的更新日志覆盖文件。
- 若用户选 [C]：到此为止，不写入。

写入成功后：判定：**CHANGELOG WRITTEN**——更新日志已保存至 `docs/CHANGELOG.md`。
用户拒绝时：判定：**COMPLETE**——更新日志已生成。

---

## 阶段 8：后续步骤

- 用 `/patch-notes [版本]` 生成风格化、可保存的公开发布版本。
- 对外发布更新日志前运行 `/release-checklist`。

### 准则

- 面向玩家的更新日志中绝不暴露内部代码引用、文件路径或开发者姓名
- 将相关变更归组呈现，而不是逐条罗列提交
- 若提交信息不清晰，查看关联文件和 Sprint 数据获取上下文
- 平衡性调整必须始终附带设计理由，而不只是数字
- 已知问题要诚实——玩家欣赏透明
- 若 git 历史杂乱（合并提交、回滚、fixup 提交），整理出清晰的叙事，
  而不是逐字罗列每个提交
